# `ms` (ms-cli) reference

The standalone CLI for the ms1 format (mnemonic-secret / ms-codec).
Twelve subcommands (including the v0.7.0 BIP-93 codex32 K-of-N
[`split`](#ms-split) / [`combine`](#ms-combine) pair). Most users will
use `mnemonic bundle` instead; `ms` is for direct secret-card
inspection or for ms1-only pipelines.

ms1 adopts BIP-93 codex32 directly via the upstream `rust-codex32`
crate (unlike md1 / mk1, which fork the BCH plumbing); `ms` is a
thin wrapper exposing the codex32 single-string mode in a
toolkit-style CLI.

Every subcommand below accepts `--help` (`-h`) for inline help.

## Secret material never goes on argv {#ms-argv-guard}

Since ms-cli 0.17.0, `ms` refuses to start when a secret sits on its
command line: an ms1 string or share, a BIP-39 phrase, or raw hex entropy,
whether positional or after a flag. argv is public — `ps` shows it,
`/proc/<pid>/cmdline` holds it, and your shell writes it to history — so
the check runs on the raw argument list *before* the parser, and a refused
command reads nothing and writes nothing. The refusal names the argument by
position (never by value), lists the private channels for that verb, and
prints a per-shell recipe to purge the line from history. Pass the secret
on one of these instead:

| you were passing | pass this instead |
|---|---|
| an ms1 string (`decode`, `derive`, `inspect`, `verify`, `hashlock`) | `--in FILE`, or `-` (or nothing) and pipe it on stdin |
| `--ms1 <value>` (`repair`) | `--in FILE`, or `--ms1 -` and pipe it on stdin |
| `--phrase <value>` (`encode`, `split`, `derive`, `verify`) | `--in FILE` (`encode`, `split`), or `--phrase -` and pipe it on stdin |
| `--hex <value>` | `--hex -` and pipe it on stdin |
| shares (`combine`) | `--in FILE`, one share per line |

`--in FILE` frees stdin, so a verb that needs two secrets (an ms1 and the
phrase to check it against, for `ms verify`) can take one from a file and
one from stdin. **`--allow-argv-secret`** (accepted by every verb that
reads a secret) proceeds anyway; use it only where argv is safe — a
single-user air-gapped box, or an amnesic Tails session.

Output can go to a file as well: **`--out FILE`** on `encode`, `split`,
`repair` and `hashlock` writes the canonical artifact owner-only (mode
`0600`, set on the open file, so an existing world-readable file is
tightened too); it overwrites and truncates. `ms gen-man --out <DIR>` is
unrelated: there it names a directory.

> **Recovering a forgotten BIP-39 passphrase.** If you have your entropy
> (an ms1 backup or seed words) but not the BIP-39 passphrase (the
> optional "25th word"), it cannot be brute-forced from the entropy alone.
> A BIP-39 passphrase has no internal verifier — every candidate yields a
> valid-looking wallet — so correctness is only definable against a value
> you already know (an address, xpub, or master-fingerprint), an
> external-derivation oracle that `ms` does not perform (`ms` only
> encodes/decodes entropy). An external open-source tool does exactly
> this: [**btcrecover**](https://github.com/3rdIteration/btcrecover)
> (maintained fork; [original](https://github.com/gurnec/btcrecover))
> searches passphrase candidates and confirms each by deriving an address
> / xpub / master-fingerprint at common default paths and matching your
> known value. Pointer current as of 2026-05-25; run untrusted recovery
> tools offline, on an air-gapped machine. This mirrors the `ms --help`
> footer.

## `ms encode`

Encode a BIP-39 mnemonic (or hex entropy) as an ms1 string.

### Synopsis

```sh
ms encode [OPTIONS] <--phrase <PHRASE> | --hex <HEX> | --in <FILE>>
```

### Flags

| Flag | Purpose |
|---|---|
| `--phrase <PHRASE>` | BIP-39 mnemonic; `-` reads from stdin (on argv it is refused — see [above](#ms-argv-guard)) |
| `--hex <HEX>` | hex-encoded entropy bytes (16/20/24/28/32 bytes = 32/40/48/56/64 hex chars); `-` reads from stdin |
| `--in <FILE>` | read the BIP-39 **phrase** from FILE. It never reads hex (use `--hex - < FILE`): a file that could be either would let a hex-alphabet phrase decode as entropy for a different wallet |
| `--out <FILE>` | write the ms1 string to FILE, owner-only (`0600`) |
| `--allow-argv-secret` | admit a phrase or hex on argv (see [above](#ms-argv-guard)) |
| `--language <LANGUAGE>` | BIP-39 wordlist for the input phrase; ignored under `--hex` |
| `--no-engraving-card` | suppress the stderr engraving-card layout |
| `--group-size <N>` | grouping for the **stderr engraving card**: a separator every N characters (default 5; `0` = unbroken). Since ms-cli 0.17.0 stdout always carries the unbroken ms1 (so `ms encode \| me sysw pack` can classify it), and so does `--json`; `--no-engraving-card` therefore discards the only grouped copy. `ms split` still groups each printed share; `ms combine` has no grouping flags and prints unbroken. Separator-stripping on intake means grouped and unbroken cards both re-ingest |
| `--separator <space\|hyphen\|comma>` | the grouping separator for `--group-size` (default `space`); keyword or the literal `-` / `,` or a space. |
| `--json` | emit a single JSON object on stdout |

### `entr` vs `mnem` payload kind (auto-routing)

`ms encode` **auto-routes** to one of two ms1 payload kinds based on the input:

- **`entr`** (byte-identical with ms-cli v0.1): produced for English phrases (`--language english`, the default) and for raw entropy (`--hex`). The payload carries only the entropy bytes. This is the classic form and is compatible with all ms-codec versions.
- **`mnem`** (ms-cli v0.2 / ms-codec 0.3.0+): produced automatically for any non-English `--phrase` (i.e. `--language` is anything other than `english`). The payload carries a one-byte language tag alongside the entropy, so that a decoder can recover the phrase in the **original wordlist language** without the caller needing to specify `--language` at decode time.

This solves the **§6.3 non-English seed footgun**: a BIP-39 seed is PBKDF2 over the *language-specific* mnemonic string, so the same entropy decoded with the wrong language yields a different wallet. With `mnem` encoding the language is preserved on the wire; `ms decode` and `ms inspect` read it back automatically.

> **Note:** `entr` ms1 strings from English sources are **byte-identical** before and after the v0.2 upgrade — existing English backups are unaffected.

### Worked example

```sh
# English phrase → `entr` ms1 (classic, byte-identical with v0.1)
# phrase.txt holds "abandon abandon … about" on one line
ms encode --in phrase.txt
# ms10entrsqqqqqqqqqqqqqqqqqqqqqqqqqqqqcj9sxraq34v7f

# Non-English phrase → `mnem` ms1 (language preserved on wire, v0.2+)
# phrase-ja.txt holds "あいこくしん あいこくしん … あおぞら"
ms encode --in phrase-ja.txt --language japanese
# ms10entrsqgqsqqqqqqqqqqqqqqqqqqqqqqqqqj9tawneveyd9j

# Write the card to a private file instead of stdout:
ms encode --in phrase.txt --out card.txt
```

## `ms decode`

Decode an ms1 string back to its BIP-39 mnemonic and entropy bytes.

### Synopsis

```sh
ms decode [OPTIONS] [--in <FILE> | -]
```

### Flags

| Flag | Purpose |
|---|---|
| `[MS1]` | the ms1 string; `-` or omitted reads it from stdin (on argv it is refused — see [above](#ms-argv-guard)) |
| `--in <FILE>` | read the ms1 string from FILE |
| `--allow-argv-secret` | admit the ms1 string on argv |
| `--language <LANGUAGE>` | BIP-39 wordlist for the output phrase |
| `--json` | emit JSON output |

### `mnem` decode behavior

When decoding a **`mnem`** ms1 string (produced by `ms encode` for non-English phrases, ms-cli v0.2+), the wordlist language is read directly from the wire payload. The `--language` flag is **not required** — the decoded phrase is automatically emitted in the language stored in the card. If `--language` is supplied and disagrees with the on-wire language, the decoder uses the on-wire value (the on-wire language is authoritative).

For classic **`entr`** ms1 strings, `--language` selects the output wordlist (default `english`; annotated `DEFAULT` on stdout and stderr when defaulted).

### Worked example

```sh
# entr ms1: `--language` selects output wordlist (default english)
# card.txt holds ms10entrsqqqqqqqqqqqqqqqqqqqqqqqqqqqqcj9sxraq34v7f
ms decode --in card.txt
# entropy: 00000000000000000000000000000000
# phrase: abandon abandon abandon … about
# language: english (12 words, default — verify against your records)

# mnem ms1: language read from wire — no --language needed
# card-ja.txt holds ms10entrsqgqsqqqqqqqqqqqqqqqqqqqqqqqqqj9tawneveyd9j
ms decode --in card-ja.txt
# phrase: あいこくしん あいこくしん … あおぞら
# language: japanese (12 words)
```

## `ms derive`

Derive the **master fingerprint** (the cheapest "did I recover the right seed?" check) and, with `--template`, an **account xpub** for watch-only setup. Read-only public derivation — **no master seed, root xprv, or private keys on stdout, and `ms` never signs** (use the toolkit's `mnemonic convert` for secret-bearing outputs).

The BIP-39 seed is `PBKDF2` over the *language-specific* mnemonic string, so the master fingerprint/xpub depend on `--language` — when it is omitted, `english` is used and annotated `DEFAULT` (stdout + stderr), exactly like `ms decode`.

### Synopsis

```sh
ms derive [<MS1>] [--hex <HEX> | --phrase <WORDS>] \
  [--template <bip44|bip49|bip84|bip86|bip48|bip48-p2wsh|bip48-p2sh-p2wsh>] \
          [--account <N>] [--network <mainnet|testnet>] [--passphrase <V> | --passphrase-stdin] \
          [--language <L>] [--json]
```

The entropy comes from one of: an `ms1` string (`--in FILE`, or stdin via `-` or omitted), `--hex` raw entropy, or `--phrase` a BIP-39 mnemonic (each of those on stdin via `-`; on argv all three are refused — see [above](#ms-argv-guard)). Without `--template` only the master fingerprint is emitted.

### Flags

| Flag | Purpose |
|---|---|
| `<MS1>` | ms1 string (positional); `-` or omitted reads from stdin |
| `--in <FILE>` | read the ms1 string from FILE |
| `--allow-argv-secret` | admit an ms1, hex or phrase on argv |
| `--hex <HEX>` | raw entropy (16/20/24/28/32 B), alternative to the ms1; `-` reads stdin |
| `--phrase <WORDS>` | a BIP-39 mnemonic, alternative to the ms1; `-` reads stdin |
| `--template <T>` | emit an account xpub at the BIP-defined default keypath for a script type. Single-sig: `bip44`/`bip49`/`bip84`/`bip86` → `m/<purpose>'/<coin>'/<account>'`. Multisig (BIP-48): `bip48-p2wsh` (native segwit, `script_type` `2'`, the BIP's recommended default) and `bip48-p2sh-p2wsh` (nested segwit, `1'`) → `m/48'/<coin>'/<account>'/<script_type>'`. A bare `bip48` is **accepted** and assumes `2'` (p2wsh), which BIP-48 itself recommends — the assumption is announced on stdout as `(DEFAULT)`, in a loud stderr note naming the alternative, and in `--json` as `script_type_defaulted`. An explicitly chosen script type announces nothing. There is no `bip48-p2tr`: BIP-48 registers no Taproot script type. |
| `--account <N>` | account index for `--template` (default 0) |
| `--network <NET>` | `mainnet` (default) or `testnet`; sets the coin-type + xpub/tpub serialization |
| `--passphrase <V>` | BIP-39 passphrase |
| `--passphrase-stdin` | read the BIP-39 passphrase from stdin (conflicts with `--passphrase`) |
| `--language <L>` | BIP-39 wordlist (load-bearing; default `english`, annotated `DEFAULT`) |
| `--json` | emit JSON output |
| `--help` | print help |

### Worked example

```sh
ms derive --in card.txt --template bip84      # card.txt: the abandon…about ms1
# master_fingerprint:  73c5da0a
# account_path:        m/84'/0'/0'
# account_xpub:        xpub6CatWdiZiodmUeTDp8LT5or8nmbKNcuyvz7WyksVFkKB4RHwCD3XyuvPEbvqAQY3rAPshWcMLoP2fMFMKHPJ4ZeZXYVUhLv1VMrjPC7PW6V
# language:            english (DEFAULT)
```

JSON mode emits `{ "schema_version":"1", "master_fingerprint", "network", "account_path"?, "account_xpub"?, "language", "language_defaulted" }` (the `account_*` fields are present only with `--template`).

## `ms split` {#ms-split}

Split a secret (BIP-39 mnemonic or hex entropy) into N **BIP-93 codex32
K-of-N shares**. Any K of the N shares recombine to the original via
[`ms combine`](#ms-combine), using codex32's native `threshold(k)` +
`index` Shamir mechanism over `GF(32)`. The whole N-share SET is
secret-equivalent — a `PrivateKeyMaterial` stderr advisory is emitted —
so engrave each share on its own backup medium. Bounds:
**2 ≤ K ≤ N ≤ 31**.

A non-English `--phrase` splits as a `mnem` share-set so the BIP-39
wordlist language survives the split; an English phrase or `--hex`
entropy splits as a plain `entr` share-set. The toolkit front-end is
[`mnemonic ms-shares split`](#mnemonic-ms-shares).

### Synopsis

```sh
ms split (--phrase - | --hex - | --in <FILE>) --threshold <K> --shares <N> \
         [--language <L>] [--out <FILE>] [--group-size <N>] [--separator <S>] [--json]
```

### Flags

| Flag | Purpose |
|---|---|
| `--phrase <PHRASE>` | BIP-39 mnemonic to split; `-` reads from stdin |
| `--hex <HEX>` | hex-encoded entropy to split (16/20/24/28/32 B = 32/40/48/56/64 hex chars), alternative to `--phrase`; `-` reads from stdin |
| `--in <FILE>` | read the BIP-39 **phrase** from FILE (never hex — the same rule as `ms encode --in`) |
| `--out <FILE>` | write the shares to FILE, one unbroken share per line, owner-only (`0600`); stdout keeps only the `share i of N:` labels |
| `--allow-argv-secret` | admit a phrase or hex on argv |
| `--group-size <N>` | display grouping for each printed share (default 5; `0` = unbroken). Unlike `ms encode`, the grouped form is what `ms split` prints on stdout; `--out` writes unbroken shares |
| `--separator <S>` | the grouping separator (`space`, `hyphen`, `comma` or the literal character), as `ms encode` |
| `--threshold <K>` | threshold K — minimum shares needed to recombine (2..=9) |
| `--shares <N>` | total shares N to produce (K ≤ N ≤ 31) |
| `--language <L>` | BIP-39 wordlist for the input phrase; ignored under `--hex`. A non-English wordlist produces a `mnem` share-set (default `english`) |
| `--json` | emit a single JSON object on stdout (`{ shares, k, n, id, kind, language? }`) instead of multi-line text |
| `--help` | print help |

### Worked example

```sh
# entropy.txt holds 00000000000000000000000000000000
ms split --hex - -k 2 -n 3 < entropy.txt
# 3 ms1-format codex32 shares, each after a `share i of 3:` label,
# threshold digit `2`, a shared random 4-char identifier,
# distinct non-`s` indices.

ms split --hex - -k 2 -n 3 --out shares.txt < entropy.txt   # shares to a 0600 file
```

Recombine any 2 with [`ms combine`](#ms-combine).

## `ms combine` {#ms-combine}

Recombine K-of-N codex32 shares (from [`ms split`](#ms-split)) into the
original secret. Supply K (or more) distributed shares with distinct
indices; the recovered secret is emitted per `--to`. The
secret-carrying share at index `s` is NEVER a valid input (it is
rejected). The recovered output is private key material (a
`PrivateKeyMaterial` stderr advisory is emitted). The toolkit front-end
is [`mnemonic ms-shares combine`](#mnemonic-ms-shares).

### Synopsis

```sh
ms combine --in <FILE> [--to <phrase|entropy|ms1>] [--json]
```

### Flags

| Flag | Purpose |
|---|---|
| `<SHARES>...` | the distributed share strings to recombine (positional; K or more, distinct indices). On argv they are refused (see [above](#ms-argv-guard)) |
| `--in <FILE>` | read the shares from FILE, one per line; display separators are stripped per line, so a grouped share typed back off metal re-ingests |
| `--allow-argv-secret` | admit shares on argv |
| `--to <T>` | output form for the recovered secret (default `phrase`): `phrase` (BIP-39 mnemonic — `mnem` → wire language, `entr` → English), `entropy` (raw entropy hex), or `ms1` (a single unshared ms1 string) |
| `--json` | emit a single JSON object on stdout instead of text |
| `--help` | print help |

### Worked example

```sh
ms combine --in shares.txt              # recover the BIP-39 phrase
ms combine --in shares.txt --to ms1     # recover a single ms1 string
ms combine --in shares.txt --to entropy # recover raw entropy hex
```

Fewer than K shares → a "threshold not passed" refusal; a repeated
index → a "repeated index" refusal; the secret share at index `s` → a
"secret share supplied to combine" refusal.

## `ms inspect`

Inspect an ms1 string's structural fields and decoder verdict
(debug-style verbose output).

### Synopsis

```sh
ms inspect [OPTIONS] [--in <FILE> | -]
```

### Flags

| Flag | Purpose |
|---|---|
| `[MS1]` | the ms1 string; `-` or omitted reads it from stdin (on argv it is refused) |
| `--in <FILE>` | read the ms1 string from FILE |
| `--allow-argv-secret` | admit the ms1 string on argv |
| `--json` | emit JSON output |

### `kind` and `language` fields

`ms inspect` reports a `kind` field distinguishing the ms1 payload variants:

- `kind: entr` — classic entropy-only payload (ms-cli v0.1 / ms-codec 0.1–0.2).
- `kind: mnem` — language-tagged payload (ms-cli v0.2+ / ms-codec 0.3.0+); the `language` field is also present, naming the stored wordlist (e.g. `japanese`).
- `kind: share` — a BIP-93 codex32 K-of-N share (ms-cli v0.7.0+; from [`ms split`](#ms-split)). Its threshold digit is `2..9` (a single-string ms1 is the unshared sentinel `0`). For a share, `ms inspect` reports `kind: share` plus the `threshold`, `id`, and `index` fields and exits 0 — it does NOT print a `threshold-not-zero` length/decode FAIL. The `prefix_byte` / payload-kind fields are SUPPRESSED for a share: a distributed share's leading data byte is an interpolated `GF(32)` value, not a meaningful payload prefix, and must not be interpreted as one. Recombine ≥K shares with [`ms combine`](#ms-combine).

- `kind: preimage` — a hashlock PREIMAGE plate (ms-cli v0.18.0+ / ms-codec 0.8.0+; from [`ms hashlock`](#ms-hashlock)): kind byte `0x03`, id `hash`, always 75 characters. Not a seed: `ms derive` and `ms verify` refuse it and name `ms hashlock` as the remedy; `ms decode` prints the kind, the preimage hex and its digest, never words.

`entr` strings do not carry a `language` line in `ms inspect` output.

## `ms verify`

Verify an ms1 string is valid (and optionally round-trips against a
phrase).

### Synopsis

```sh
ms verify [OPTIONS] [--in <FILE> | -]
```

### Flags

| Flag | Purpose |
|---|---|
| `[MS1]` | the ms1 string; `-` or omitted reads it from stdin (on argv it is refused) |
| `--in <FILE>` | read the ms1 string from FILE — which frees stdin for `--phrase -` |
| `--allow-argv-secret` | admit the ms1 string or phrase on argv |
| `--phrase <PHRASE>` | optional BIP-39 phrase to round-trip against (exit 4 on mismatch); `-` reads it from stdin |

| `--json` | emit JSON output |

```sh

# OK: round-trip valid (12 words, language=english)
```

## `ms hashlock` {#ms-hashlock}

Derive a 32-byte hashlock **preimage** from a phrase (or take one you already
have), print the public `hash:` record for the wallet-policy composer, and back
the preimage up as an ms1 plate string of its own kind (`0x03`, id `hash`).
ms-cli v0.18.0+ / ms-codec 0.8.0+. The phrase is a *hashlock phrase*, not a
BIP-39 passphrase: it unlocks one spend path of a policy, and a spent preimage
is public on-chain, so use one phrase per policy.

### Synopsis

```sh
ms hashlock --kind <KIND> --hashlock-phrase-stdin [--method hardened|sha256] [--out FILE] < phrase.txt
ms hashlock --kind <KIND> --hex <HEX> | --hex -     # an existing 32-byte preimage
ms hashlock --kind <KIND> --random --out FILE       # draw one; the file is the only copy
ms hashlock --kind <KIND> --in FILE | -             # re-derive the digest from a plate
```

`<KIND>` is `sha256`, `hash256`, `ripemd160` or `hash160`. `--kind` is optional
but belongs in every command you write down (see the flag below).

Exactly one source per invocation: `--hashlock-phrase`, `--hashlock-phrase-stdin`,
`--hex`, `--random`, or an ms1 plate (`<MS1>`, `-`, or `--in FILE`). Zero or two
sources exit 64.

### Flags

| Flag | Purpose |
|---|---|
| `--hashlock-phrase <TEXT>` | the phrase on argv — a SECRET channel, refused unless `--allow-argv-secret`; the literal `-` is refused too (use `--hashlock-phrase-stdin`) |
| `--hashlock-phrase-stdin` | read the phrase from stdin byte-verbatim (one trailing newline stripped; no trimming, no case folding); at a terminal, one line |
| `--kind <KIND>` | which hash the wallet's SCRIPT commits to: `sha256`, `hash256`, `ripemd160` or `hash160` (lowercase; any other case is refused, exit 64, never folded). It chooses the stdout record: `hash:<hex>` for `sha256`, `hash:<kind>:<hex>` for the other three. **Omitted**, stdout still carries the `sha256` record and stderr lists the preimage's digest under all four kinds (under `--json`: `digests_by_kind` and `kind_specified: false`), because a plate cut before this flag existed records no kind and a lookup beats an impossible check. Since a pipe reads only stdout, a `ripemd160` wallet driven without `--kind` packs a `sha256` payload — so write `--kind` into every command you record |
| `--phrase-looks-like-digest-ok` | proceed with a phrase that is exactly 40 or 64 hex characters (either case). Such a phrase is very likely a DIGEST the operator means to commit to, and hashing it commits the wallet to the ASCII of those characters instead, a preimage nobody holds. Without this flag that phrase stops with exit 1 and names the digest's real destinations (`md compose --path '...,<kind>=<digest>'`, `me sysw pack 'hash:[<kind>:]<digest>'`); with it, the phrase is hashed like any other. A warning you must acknowledge, not a refusal |
| `--hex <HEX>` | an existing preimage: exactly 32 bytes (64 hex characters); `-` reads stdin |
| `--random` | 32 bytes from the OS random source; **requires `--out FILE`**, and never overwrites an existing file |
| `--method <METHOD>` | phrase → preimage: `hardened` (default: PBKDF2-HMAC-SHA256, salt `ms-hashlock-v1`, 100,000 iterations) or `sha256` (one SHA-256 of the phrase bytes — the brainwallet construction; always warned) |
| `--in <FILE>` | read the ms1 plate string from FILE (the same meaning as the other reading verbs) |
| `--out <FILE>` | write the preimage plate string here, owner-only (`0600`); never suppresses stdout |
| `--json` | one JSON object on stdout in place of the `hash:` line; it carries the secret, so the private-key-material advisory fires |
| `--no-engraving-card` | suppress the stderr card |
| `--group-size <N>` | group the plate string on the card every N characters (default 5; 0 = none) |
| `--separator <SEP>` | `space`, `hyphen`, `comma` or the literal character, as `ms encode` / `ms split` |
| `--allow-argv-secret` | admit a secret on argv (see `ms encode --help`) |

The phrase rule: non-empty, printable ASCII (`0x20..=0x7E`), at most 100
characters, and never an ms1-shaped string (that is a plate, not a phrase — use
the plate channel). A phrase of exactly 40 or 64 hex characters stops unless
`--phrase-looks-like-digest-ok` confirms it (see the flag). The phrase's bytes
are used verbatim: `Correct Horse` and `correct horse` derive different
preimages.

**By hand, the recipe "hash the phrase to 32 bytes" is `--method sha256`, not
the default.** The default `hardened` method runs PBKDF2 so a memorable phrase
is not a brainwallet; a policy that recorded its preimage as plain SHA-256 must
be re-derived with `--method sha256`. The method is a permanent property of the
policy: the card prints the method line so it can be documented outside the tool.

### Outputs

- stdout: the public digest record, in the spelling `me sysw pack` reads from
  stdin (`ms hashlock --kind … | me sysw pack --out payload.bin`):
  `hash:<64 hex>` for `sha256`, `hash:hash256:<64 hex>`,
  `hash:ripemd160:<40 hex>` or `hash:hash160:<40 hex>`. The `hash256` tag is
  the only thing telling its record from a `sha256` one (both are 64 hex), so
  it is never to be stripped.
- stderr: the engraving card; its first line says it carries the preimage.
  Without `--kind`, a four-line table of the digest under every kind. With a
  non-`sha256` kind, notes that `me sysw pack` and the SeedHammer II firmware
  must both support that kind.
- `--out FILE`: the 75-character plate string `ms10hash…`, kind `0x03`.

### Worked example

```sh
$ printf 'correct horse battery staple' > phrase.txt
$ ms hashlock --kind sha256 --hashlock-phrase-stdin < phrase.txt
hash:3cf5d421caf2a9c8eb9de1d400866ea7d475e6ba978861bb0167a37cb70a4c12
$ ms hashlock --kind sha256 --hashlock-phrase-stdin --method sha256 < phrase.txt
hash:b867db875479bcc0287352cdaa4a1755689b8338777d0915e9acd9f6edbc96cb
$ ms hashlock --kind ripemd160 --hashlock-phrase-stdin < phrase.txt
hash:ripemd160:09e7bb5051d89788fb4e4b374126721dbcc2946b
$ ms hashlock --kind sha256 --hashlock-phrase-stdin --out preimage.txt < phrase.txt >/dev/null
```

anchor row; `correct horse battery staple` is THE brainwallet phrase and is
used here precisely because its `sha256` digest is a known, swept key.)

### On the SeedHammer II {#hashlock-on-the-seedhammer}

The wallet-policy composer on the SeedHammer II can derive a hashlock preimage
from a typed phrase without a host, and it runs the same rule and the same
parameters as `ms hashlock` above: the phrase bytes verbatim, salt
`ms-hashlock-v1`, 100,000 PBKDF2-HMAC-SHA256 iterations, digest = SHA-256 of the
32-byte preimage. The same phrase typed on the machine and fed to
`ms hashlock --kind sha256 --hashlock-phrase-stdin` yields the same `hash:` record — that
equality is the point of the whole route, and the device asks you to check it
before you fund the wallet.

Firmware: the m-format SeedHammer fork, branch `hashlock-h2` (not yet in a
tagged firmware release). Screens are quoted from that firmware.

**Where it is.** Editing a spend path's hash opens `Path N hash`, whose rows are
one per `hash:` record in the loaded payload, then `Type a hashlock phrase`,
`Type 64 hex`, and `No hash lock`. The lead is `Which hash?`, or, when the
payload carries no `hash:` record at all:

> No hash record in the payload. Type a phrase below, or make one with ms
> hashlock on the host.

Choosing any row that *takes* a hash — a payload row, the phrase row or the hex
row — first shows the rule the composer states everywhere it accepts a digest:

> The hash must be SHA-256 of a 32-byte value. A passphrase must be hashed to 32
> bytes first, then hashed again. A hash of the passphrase itself can never be
> spent.

#### The `Hashlock phrase` screen

Its lead answers that rule directly:

> This screen does that hashing for you. Use a phrase you have never used
> anywhere else.

Below it sits an `n/100` counter and a four-page touch keyboard. The pages —
lowercase, uppercase, digits and symbols, and a fourth page of the thirteen
symbols the first three omit — together type exactly the 95 printable-ASCII
characters `0x20..=0x7E` and nothing else; the function row is page-cycle,
`space`, `show` and backspace.

**The phrase rule is the host's, byte for byte.** Nothing on this screen trims,
case-folds, collapses runs of spaces or normalises anything: `Correct Horse` and
`correct horse` are different phrases, and a trailing space is a character that
changes the digest. The counter is unclamped — type past the cap and it keeps
counting, `101/100` and beyond — and the rule is applied when you press the
checkmark, in the host's order:

| The phrase | What the screen says |
|---|---|
| is empty | `Type a hashlock phrase, or press Back.` |
| has a byte outside `0x20..=0x7E` | `A hashlock phrase is printable ASCII only.` |
| is an ms1-shaped string | `That is a preimage plate, not a phrase. On the host, run ms hashlock with it and load the hash: record it prints.` |
| is longer than 100 characters | `A hashlock phrase is at most 100 characters.` |
| is exactly 64 hex characters | `That is a preimage in hex, not a phrase. Use the Type 64 hex row.` |

Read the order literally: the ms1 test runs **before** the length cap, so a
pasted-in plate string longer than 100 characters is named as a plate rather
than as an over-long phrase — the same order `ms hashlock` applies, so the two
never disagree about what a given string is. The printable-ASCII row is not
reachable from this keyboard (it cannot type a non-printable byte); it is there
so the rule is the format's and not the keyboard's. Dismissing any refusal
returns you to the screen with what you typed still in place.

#### Method

`Hashlock method` offers `Hardened (about 10 s)` and `SHA-256`. Either can
raise a hold-to-confirm warning before it derives: the body below, then
`Hold button to confirm.`, with Back declining and returning to the pick.

`SHA-256` warns every time:

> This is the brainwallet construction: anyone holding the digest tests 10^10
> phrases per second. A phrase a person chose is not safe here; use six diceware
> words. If you have used this phrase anywhere else, press Back and choose
> another. Continue?

`Hardened` warns only when the phrase is shorter than 20 characters — at 20
characters or more it derives with no warning at all:

> Even a 20-character phrase falls in about 72 days on one GPU, and shorter ones
> fall sooner. Choose it from a generator. If you have used this phrase anywhere
> else, press Back and choose another. Continue?

`SHA-256` is instant. `Hardened` runs the 100,000 iterations on a `Deriving`
screen showing a percentage and, until the first slice has actually been timed,
the lead `Deriving. This takes about 10 seconds.`; after that it is
`About N seconds left.` from the measured rate. About ten seconds on this
machine — 100,000 iterations at a measured 9,715 per second. The screen holds
the display awake for the duration, and its discard button abandons the
derivation with nothing assigned.

#### Confirm, and reconcile against the host

The confirm modal is titled `Hash lock` and abbreviates the digest to its first
and last eight hex characters. For the chapter's worked-example phrase
(`correct horse battery staple`, hardened) it reads:

```text
hash  3cf5d421..b70a4c12
method: hardened   chars: 28
Write down this phrase, the method and this digest now. This composition holds
them until it ends. Without both, this path can never be spent.
One phrase per policy. Never use this phrase as a passphrase or a password
anywhere else.

Hold button to confirm.
```

(The second sentence used to read *"The phrase and method are not on this
device."* That became false in the H6 firmware, which holds both for the life of
one composition so it can offer to engrave them; the screen was changed with it.
Write them down anyway — a composition ends when you leave it.)

(Line breaks are the device's paragraph breaks; the prose itself wraps to the
panel, not as shown here.)

When the payload carries `hash:` records, a relation line is inserted after the
`method:` line — `matches hash 1 in the payload`, or `no hash: record in the
payload has this digest` — and a further line follows it when another path of
the same policy already carries a *different* hash. Hold the button to assign
the hash; Back declines and returns to the method pick with nothing assigned.

Assigning it draws one more screen, for every policy that gets a hash this way:

> hash  3cf5d421..b70a4c12
> method: hardened   chars: 28
> Before you cut plates, run ms hashlock with this phrase and method on the
> host and check the digest matches. If they differ, do not fund this wallet:
> build it again.

That is the reconciliation, and it is worth doing on the machine you will
actually spend from. `ms hashlock --kind sha256 --hashlock-phrase-stdin < phrase.txt` prints
`hash:3cf5d421caf2a9c8eb9de1d400866ea7d475e6ba978861bb0167a37cb70a4c12` for the
phrase above; its first and last eight characters are what the confirm screen
showed, and the same run's engraving-card stderr prints `phrase:          28
characters`, the host counterpart of the reconcile screen's `chars: 28`. A
phrase that reconciles is a phrase you typed correctly; a phrase that does not
is a path you could not have spent, discovered now rather than at spend time.

#### What Back does

Every Back inside the route, before the hold, moves one step back within it
and keeps the phrase. Only Back at the phrase screen leaves.

| Pressed at | Goes to | The typed phrase |
|---|---|---|
| `Hashlock phrase` | `Path N hash` | dropped |
| `Hashlock method` | `Hashlock phrase` | kept, ready to edit |
| either method warning (Back declines) | `Hashlock method` | kept |
| `Deriving` (the discard button) | `Hashlock method` | kept; nothing assigned |
| the `Hash lock` confirm | `Hashlock method` | kept; no hash assigned |
| the reconcile screen | the spend-path list | dropped; the hash is already assigned |
| `Path N hash` | out of the hash editor, no hash set — and if the path was being created, the new path is discarded with it | — |

#### The readout, and how much it shows

The keyboard's readout line above the keys is masked by default, one `*` per
character, and the `show` key toggles it to cleartext and back. Its height
budget on this screen is one line with no margin to spare, so a long phrase is
clamped to its **tail**: the characters you just typed stay visible and the head
scrolls out of sight. The `n/100` counter, not the readout, reports the true
length, and the confirm screen's `chars:` count is the length the device hashes.
(An earlier build of this screen drew no readout at all; that was F-481, fixed
before the H2 leg merged.)

#### Cutting the preimage onto a plate {#hashlock-preimage-plates}

The H2 firmware above derives a digest and keeps nothing. The **H6** firmware
can put the preimage itself onto steel, on a plate of its own that is stamped
`NOT A SEED`. There are two forms, and both carry a locator block so a
year-later reader knows what the plate unlocks.

| form | what is engraved | when it is offered |
|---|---|---|
| `preimage string` | the 75-character ms1 kind-`0x03` string — byte for byte what `ms hashlock --out` writes, and what `ms hashlock --in` reads back | always |
| `phrase + method` (and `phrase + method + QR`) | the hashlock phrase in plain text, plus the method line, plus optionally a QR of both | only when the machine actually holds the phrase — a preimage that arrived as a plate string has no phrase to engrave |

The offer is made at Done, one screen per held preimage, with a fourth row
`do not cut this preimage`. Whatever you choose, the plate census before the
first cut lists each accepted plate by spend path and by the digest's first and
last eight characters, says it is **not** part of the backup, and tells you to
store it apart from the policy plates and from the others. Preimage plates are
cut **first**, so there is never a window in which the policy plates exist and
the preimage does not.

**The plate is not a backup of your wallet — it is a bearer instrument.**
Whoever holds it can spend any key-less hashlock path it unlocks. That is why
the offer is per-plate, why the census says so twice, and why the host makes you
opt in (below).

##### The QR text

The QR, when you take it, encodes three LF-separated labelled lines with no
trailing newline, the phrase last:

```text
hashlock v1
method: pbkdf2-hmac-sha256 iterations=100000 salt=ms-hashlock-v1 dklen=32
phrase: <phrase>
```

For the `sha256` method the middle line is exactly `method: sha256`.

Three things about it are deliberate. `hashlock v1` versions the **text**, not
the derivation — a future parameter set gets `hashlock v2`. The method line
names the algorithm in full, so a reader with the plate and no tool can
reproduce the derivation by hand; the device builds it from its own parameter
constants rather than from a literal, so a parameter change cannot leave a plate
lying. And the phrase is the **last** line because a phrase may itself contain
`:` and spaces: everything after the `phrase:` label on the final line — one
space after the colon — is the phrase, verbatim, with real spaces.

**`ms hashlock` does not parse this text yet.** The text is fixed and pinned by
corpus rows so that plates cut now stay readable, but there is no
`ms hashlock --qr-text` or equivalent: reading a phrase-form plate back today
means retyping the phrase and the method into
`ms hashlock --hashlock-phrase-stdin --method …`. The parser is a follow-on.
The plate is complete without it — the printed text is authoritative and the QR
is a convenience over it.

##### Getting a preimage INTO a payload: `me sysw pack --pack-preimage`

`me sysw pack` refuses preimage material by default. One flag admits both
carriers:

```sh
# a plate string ms hashlock already wrote, plus its public digest record
$ ms hashlock --kind sha256 --hashlock-phrase-stdin --out preimage.txt < phrase.txt > records.txt
$ cat preimage.txt >> records.txt
$ me sysw pack --pack-preimage --no-passphrase --in records.txt --out payload.bin
```

| carrier | wire form |
|---|---|
| a preimage | the bare ms1 kind-`0x03` string, id `hash`, 75 characters — exactly the `--out` file, not a re-encoding of it |
| a phrase | `phrase:<hex of the UTF-8 text "<method>,<phrase>">`, where `<method>` is `hardened` or `sha256` — the `now:` record's idiom, cut on the **first** comma so the phrase may contain commas |

`phrase:` joins `key:`, `hash:` and `now:` as a reserved record prefix, so a
`phrase:` record whose body is not valid lowercase hex is refused rather than
treated as free text; the phrase inside it must pass the same rule
`ms hashlock` applies (non-empty, printable ASCII, not ms1-shaped, at most 100
characters). `me` 0.11.0 does not repeat `ms hashlock`'s stop on a phrase of
exactly 40 or 64 hex characters: it packs such a phrase, so run it through
`ms hashlock` first.

Two things to know about the flags. **`--pack-preimage` is not
`--seal-secret`** and the two do not substitute: one admits bearer spend
material into a payload, the other encrypts seed material. And **`--in` is
required here, not stylistic** — both carriers are bearer material, so the argv
guard refuses them on the command line before the parser runs. Put them in a
file.

**`ms hashlock --emit-record` writes the `phrase:` record.** It prints one on
the card beside the preimage, built from the phrase it has already read, so the
hex never has to be assembled by hand. It needs a phrase source: `--hex`,
`--random` and an ms1 input carry no phrase, and asking for a record there is a
usage error rather than a silent omission. The record carries the phrase, so it
goes on the card and never on stdout, which still carries only the public
digest.

## `ms repair`

BCH error-correct a single ms1 string (`ms-cli v0.4.0`+). Wraps
`ms_codec::decode_with_correction` (ms-codec v0.2.0+) and renders a
single-chunk repair report. The string is corrected within the
`BCH(93,80,8)` `t=4` capacity (up to four substitution errors).

`ms repair` is the per-codec sibling of toolkit's `mnemonic repair`
(see `41-mnemonic.md` `## mnemonic repair`). The two surfaces share
the same `RepairJson` envelope schema byte-exact (cross-CLI parser
reuse — D27 of the toolkit v0.22.x follow-ups cycle plan).

Single-HRP context: no `--hrp` flag. ms1 is single-chunk by codex32
specification (HRP `ms` is always single-string `BCH(93,80,8)`); no
variadic positional.

### Synopsis

```sh
ms repair [OPTIONS] <--ms1 - | --in <FILE>>
```

### Flags

| Flag | Purpose |
|---|---|
| `--ms1 <MS1>` | ms1 string to attempt to repair; use `-` to read the string from stdin (a single line). A literal ms1 here is refused (see [above](#ms-argv-guard)) |
| `--in <FILE>` | read the ms1 string from FILE |
| `--out <FILE>` | write the corrected ms1 to FILE, owner-only (`0600`) |
| `--allow-argv-secret` | admit the ms1 string on argv |
| `--json` | emit a single JSON envelope on stdout instead of the text-form report; schema byte-matches `mnemonic repair --json`'s `RepairJson` shape |
| `--help` | print help |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | input already valid; no correction applied; echoed unchanged. |
| `4` | **`VERIFY-ME` Candidate** (Cycle F, `ms1-repair-demote-to-candidate` — a funds fix) — at least one substitution corrected; stdout = repair report + corrected string; stderr carries an UNVERIFIED advisory. **Never exit 5** — see below. |
| `2` | unrepairable (BCH-uncorrectable: > 4 substitution errors, or structural ms1 error before correction could run). |
| `1` | I/O error or other generic failure. |

**No self-verification, no exit 5 (Cycle F funds fix).** `ms1` encodes
raw BIP-39 entropy as a single codex32 string — a bearer secret with no
cross-chunk hash, no fingerprint, and no internal redundancy beyond the
BCH checksum itself. A bounded-distance (≤4-error) substitution
correction is provably the original string, but beyond that bound the
correction can still *succeed* while **aliasing to a DIFFERENT, valid
seed** — and unlike `mk1`/`md1`, there is nothing else to catch it.
Before this cycle, `ms repair` reported any correction as a confident
exit-`5` `REPAIR_APPLIED`; it now **always** demotes a touched
correction to an exit-`4` Candidate, with a stderr advisory recommending
the user confirm the derived address/xpub against a known-good copy
before trusting it. `ms repair` has no `--max-indel` flag (unlike
`mnemonic repair --ms1 --max-indel`, which keeps a UNIQUE full-checksum
indel recovery at exit `5` — a genuinely different, stronger-verified
mechanism; see `41-mnemonic.md`'s `mnemonic repair` chapter), so exit
`5` is unreachable from this binary entirely. BIP-93 recommends
confirming a corrected codex32 string before relying on it; this
demotion operationalizes that recommendation. The **principled rule
across all four CLIs** (D26 of the v0.22.x follow-ups cycle, refined by
Cycle E + Cycle F): exit-5 `REPAIR_APPLIED` means a correction is
**verified now** or **verifiable-by-reassembly later** (mk1/md1's
cross-chunk structure); exit-4 `VERIFY-ME` means a substitution
correction spent the checksum's error-detection budget with **no
self-oracle** — `ms1`'s case, always.

### Worked example

```sh
# broken.txt holds a valid ms1 chunk with one character corrupted
# (position 17 'q' → 'z'): ms10entrsqqqqqqqqqqqzqqqqqqqqqqqqqqqqcj9sxraq34v7f
ms repair --in broken.txt
```

describes the fix):


### D9 secret-on-stdout advisory

Because the corrected output carries the ms1 (which encodes BIP-39
entropy), the D9 secret-on-stdout advisory fires: a stderr line
recommending the user pipe the output to a file or to an encryption
tool to avoid scrollback exposure. This advisory is informational and
does not affect the exit code — it fires alongside, not instead of, the
UNVERIFIED Candidate advisory above.

### `--json` verdict field (Cycle F)

`ms repair --json`'s `RepairJson` envelope gained a `verdict` field
(`"blessed"` for a clean input, `"candidate"` for a touched correction),
at the identical field position as `mnemonic repair --json`'s envelope
(the D27 byte-match invariant this chapter's intro references).
