# `mr` (mr-cli) reference

<!-- cspell:ignore gylyp qqsqs qpzry tvdw khce -->

The standalone CLI for the Refugium mr1 format (mnemonic-refugium /
mr-codec). An mr1 card describes a whole set of wallets: one template
(a BIP-388 wallet policy), an epoch axis that moves its deadlines
forward, and a table of slots (rows) that change the template per
wallet. Each wallet of the set is a *member* (e, s): epoch e, slot s.
The card also carries the (0, 0) member as an md1 card.

This chapter mirrors mnemonic-refugium's `mr-cli`: the writers
`create` and `upgrade`, and the read-side verbs `verify`, `decode`,
`repair`, `member`, `address`, `current`, `units` and the heir's
`export`.

:::primer
A *slot* is a row of the card's slot table: slot 0 is the template as
written, and each further slot changes some of its units (switches a
branch off, shifts a deadline, adds a wait). An *epoch* moves every
deadline of the template forward by the card's delta, so the same slot
at a later epoch is a new wallet with later deadlines. `current` tells
you which epoch to use now; `member` and `address` hand out that member.
:::

Every subcommand below accepts `--help` (`-h`) for inline help. Each Flags table quotes `mr <verb> --help` verbatim.

## Conventions

| Topic | Rule |
|---|---|
| Card input | The positional `<mr1>...` is one card: a single `mr1` string, or every string of a chunk set, in order. A chunk set is always one card, never several. It may come before or after the options: `--keys`, `--seeds`, `upgrade`'s `--sibling-keys` and `export`'s `--try-seatings` take every value up to the next flag, but an `mr1` string among their values (no key or seed starts `mr1`) is read as the card, in the order typed, also after two such flags in a row, so `mr verify --network testnet --keys mk1… mk1… mr1…` and `mr verify --network testnet --seeds ms1… --keys mk1… mr1…` work; `upgrade` reads an `md1` string there as its card the same way, and refuses an `mr1` string typed there as ``an md1 card argument is an mr1 string`` |
| Checksums | Every reading verb **verifies only**: a string that is not a valid codeword is refused (`the mr1 checksum does not verify`), never corrected silently; the refusal ends with the string's own length (``; the string has 72 characters, `mr1` included: a character left out or added fails the checksum and `mr repair` cannot correct it, so count the engraved characters and compare them with 72, and with the card length on your kit notes' digest line, where it has one (the `card length` line `mr create` or `mr upgrade` printed)``), the number to count the engraving against (its characters as the codeword reads them, `mr1` included: spaces and hyphens typed between groups are not counted, so a string typed in groups of 4 gets the same count as one typed whole; a card given as a flag value, `export --card` or `create`'s and `upgrade`'s `--sibling` and `--bundle-card`, is read the same way): a kit written before this release has no length on its digest line, and the engraving can always be counted against the typed length. On a chunked card each such refusal of a string adds which entry of the kit's `card length` line it is compared with (``; string 0 is the first string given, and `mr` takes a card's strings in any order: compare its length with its own chunk's entry in the kit's `card length` line (the chunks in the card's order, `2 of 64` being two chunks of 64), where the kit gives one; it is chunk 0 when the strings are typed in the card's order``), since the line lists every chunk's length in chunk order and a typed length can match the wrong entry. The string layer's two length refusals gain the same count and pointer, in every verb that reads a card and in `repair`: a string over 93 symbols after `mr1` (a character added to a full 96-character string meets this before its checksum is read) is refused ``the string has 94 symbols after mr1; the regular code allows at most 93 (80 data plus 13 checksum); the string has 97 characters, `mr1` included: a character added makes a string too long, and `mr repair` cannot correct it, so count the engraved characters and compare them with 97, and with the card length on your kit notes' digest line, where it has one (the `card length` line `mr create` or `mr upgrade` printed)``, and a string under 13 ``the string has 12 symbols after mr1; it needs at least the 13-symbol checksum; the string has 15 characters, `mr1` included, fewer than any card string has: check that the whole string was given, in one argument or quoted whole, and compare it with the card length on your kit notes' digest line, where it has one (the `card length` line `mr create` or `mr upgrade` printed)`` (every string ends in its 13-symbol checksum, so such a string was cut short or split; `mr1-` is counted 3, and a lone `mr1` keeps its own refusal, below). The refusal's "string 2" counts the strings as typed, from 0: typed in the card's order, string 2 is chunk 2, whose engraved length is at place 2 (from 0) of the kit line's runs, each run filling as many places as its count. Correction is `mr repair`'s job. A string that mixes upper and lower case is refused with its next step: ``the string mixes upper and lower case (BIP 173 forbids mixed case): type it again in one case (all lower case, as `mr create` prints it)``. The same holds for each string of an mk1 plate given with `--keys`, `--keys-file` or `--sibling-keys`, in every verb that reads one: a string that needs a correction is refused, ``key <k>, string <j> of <n>: the mk1 checksum does not verify: a character was typed or engraved wrong (`mk repair` corrects up to 4 substituted characters and names them); check what you typed against the plate, then type it again, or re-engrave the plate if the plate itself is wrong``, and one beyond correction ``… does not verify and cannot be corrected: more than 4 substitutions, or a character left out or added (which `mk repair` does not correct): count its characters and check each against the plate; `mk repair` corrects up to 4 substituted characters; string <j> has <N> characters, `mk1` included, spaces and hyphens not counted: count the engraved characters and compare them with the plate: each string of an mk1 plate but its last has 111``, one text for every string whatever order the strings were typed in (\<j\> counts them as typed; 111 is the length of every string `mk encode` prints for a plate but its last) |
| Network | `--network <NETWORK>` is global: `main` (the default; `mainnet` is accepted as an alias), `signet`, `testnet` or `regtest`. It picks the address format, `xpub` or `tpub`, the tip anchor and the coin type. Any other value is a usage error. A card on the path convention carries its purpose number (270028; its keys sit at `m/270028'/<coin>'/<32r + i>'`) but not its network: a run with no `--network` is a mainnet run, and `create` and `upgrade` mint mainnet cards. The one refusal for a missing `--network`: a hand-out or an import (`address`, `member` with or without `--for-spend`, and `export`) from a path-convention card that keys a seat by xpub (its Pubkeys TLV) is refused, exit 1, before any seat is filled (`export` refuses before it prints anything): ``this card keys seats @0, @1 by xpub, and neither the card nor its xpubs record a network: rerun with the network its kit notes name (`--network main`, `--network signet`, `--network testnet` or `--network regtest`)``. A card with explicit origin paths is not refused (the coin-type warning below covers it). A path-convention card whose purpose number is not 270028 is refused as undecodable: ``purpose number <v>: this version's cards carry 270028; a card a pre-release build minted at the provisional purpose number 499' reads this way, so this card is one of those, or is damaged: re-mint it with this release: `mr create` mints a new wallet on this release's paths, so move any funds with the old build first; `mr upgrade` of its (0, 0) md1 keeps that one wallet's own paths and keys, so coins at its (0, 0) addresses stay; move any coins at the card's other members with the old build first`` (a card a pre-release build minted at the provisional `499'` has no purpose field, so its bits read as another number, `0` or `1`, or as a non-minimal varint, which reads ``the header's purpose number varint is not minimal; <the same sentence>``, or a header that ends inside the field, which reads ``the card header ends inside its purpose number field; <the same sentence>`` in every verb; `mr repair` of such a string prints the same sentence and does not send you to check the engraving; when repair changed characters it keeps the caveat, ``: `mr repair` corrects up to 4 substitutions per string, and a string with more errors can be corrected to another valid string``). A card with explicit origin paths (an upgraded md1's) may record a coin type there (each path's second step `0'` or `1'`); read on a `--network` of the other coin type, given or the default, it is read on that network all the same, with a warning: ``warning: this card's origin paths carry coin type 1' (signet, testnet and regtest), but --network is main: the card is read on main, as given; if the wallet is on signet, testnet or regtest, rerun with …`` (with no `--network`, ``--network is main (the default): the card is read on main; …``); in a run of several cards `export` tags it with the card, as it does its other card-level warnings: ``warning: card 1 [5bdd396d]: this card's origin paths carry coin type 0' (mainnet), but --network is signet: …``, once per card. Such a step need not be a coin type (Core's `m/0'/0'/k'`), and read-side verbs work on any network; `upgrade` warns the same way when the md1's paths carry the other coin type, so a mainnet-path md1 upgraded on signet reads back on signet. A plate at a seat's path under the other coin type is set aside naming the network (``plate at m/270028'/1'/0': no seat of this card with `--network main`; it is seat @0's path on a test network: rerun with …``), and a seat left empty by it is refused the same way (`seat @0, letter A: no seed and no plate given; plate 1 at … is this seat's path on a test network: rerun with …`); the plate's own set-aside line is then folded into that seat's note, which names it, and is not printed beside it. When every set-aside plate is at a seat's path under the other coin type, the run also warns ``warning: these plates are for mainnet; rerun with `--network main` `` (for a test network's plates: ``… rerun with `--network signet`, `--network testnet` or `--network regtest` ``). `export` and `member --for-spend` give the same other-network sentence for a seat left empty by such a plate, not "perhaps a plate of an earlier set"; `export` keeps it in the seat's line on stdout and in the heir file too, not on stderr alone, so a saved stdout carries it (``…, plate 1 at m/270028'/1'/0' is this seat's path on a test network: rerun with `--network signet`, …``). Beside the ``these plates are for …`` warning, `export` and `verify` print the rerun once: the seats' notes on stderr (`export`'s seat warnings and the stderr copy of its stdout line, `verify`'s refusal) end at ``… is this seat's path on a test network``, while `export`'s stdout line keeps the tail; `member` and `address` keep it. When other keys given are at the run's network, a rerun with another `--network` would break them, so the odd key is named and the flag kept: ``warning: this plate is for mainnet, while the other keys are on a test network: keep `--network` as it is, and export it again at the seat's path on a test network`` (``these plates``, ``this record``, ``these records`` or ``these keys`` as they are; the reverse for a test network's key on a mainnet run), its set-aside line ends ``; it is seat @1's path on mainnet, while the other keys are on a test network: keep `--network` as it is``, and the empty seat's refusal ends ``…, and export this seat's key again at m/270028'/1'/1'``. `create` leads with ``every key is at its seat's path on mainnet: …`` only when no key is at the run's network; with a mix, the odd key's line ends ``; it is this seat's path on mainnet, while the other keys are on a test network: keep `--network` as it is``. When `--network` was not given (mainnet by default), or the odd keys outnumber those at the run's network, the run's network may be the wrong one, and each line that names the odd keys (the note, the refusal, `export`'s per-seat earlier-set warnings and each of `create`'s odd-key lines) ends with the other remedy: ``; or, if this wallet is on a test network, rerun with `--network signet`, `--network testnet` or `--network regtest` and export the other keys again there`` (on a test-network run, ``; or, if this wallet is on mainnet, rerun with `--network main` and export the other keys again there``); the per-key set-aside line keeps its one remedy. `units` reads a card on any network |
| Miniscript text | Every template, member, policy and descriptor `mr` prints spells md1's constants as rust-miniscript does, so that a Coldcard (whose parser has no bare `0` or `1`) and Bitcoin Core both read it: `and_v(X,1)` as `t:X`, its letter joined to the wrapper letters (`tv:older(144)`), `or_i(0,X)` as `l:X` (`sln:older(144)`), `or_i(X,0)` as `u:X`, and `andor(X,Y,0)` as `and_n(X,Y)`. A constant that no such form covers (`andor(X,0,Z)`) prints bare, and `create` and `upgrade` warn on it (see `mr create`). A member whose row adds a lock (`add-wait`, `add-deadline`) is written in its cheapest form, the lock joined to the path it guards: `andor(pk(@0),older(3),…)`, not `andor(pk(@0),tv:older(3),…)`, and `and_v(v:pk(@0),older(144))` where the path ends in a signature check. That written form is the member that `member`, `address`, `export`, `verify` and the recovery steps print and derive. The guardrails judge the row on its checked form, which has the same paths and locks; a member whose checked form fails its type or sanity check is not rewritten, and keeps its checked script. If the written form ever failed its type or sanity check where the checked form passes, that would be a bug in `mr`, never a refusal of the row. `mr` runs that check once per slot (types and sanity, the script limits aside, do not depend on lock values), so such a failure names the slot: `create` and `upgrade` exit 1, issuing nothing, with ``mr: internal error (a bug): the written form of every valid member of slot <s> fails its type or sanity check; please report it``; `export` (`--try-seatings` included) and `verify` skip every member of that slot and derive the other slots, and `export`, `verify` and `decode` print the same line on stderr as ``note: internal error (a bug): the written form of every valid member of slot <s> fails its type or sanity check; please report it``, and `verify` then exits 1; `member` (with or without `--for-spend`) and `address` exit 1 with the line for the member asked for, ``mr: internal error (a bug): the written form of the member at epoch <e>, slot <s> fails its type or sanity check; please report it``. `mr units` and `decode` mark an operation whose written form would fail, as a row's only operation, ``internal error (a bug): its written form fails its type or sanity check; please report it``, and list the other units as before |
| Tip | The tool never reads the machine's clock. Every verb that measures a deadline takes the chain tip as `--height H --time T` (the median time past, unix seconds; `--time` takes any u32) and prints `tip = <height>, ≈ <date>; this must be the current tip` first. On mainnet a tip whose height and time disagree with the release's anchor by more than 180 days is refused unless `--accept-tip`; off mainnet it only warns. On testnet (testnet3, whose min-difficulty blocks decouple height from time, and whose anchor is its genesis block) the check gives one line in place of that text, ``warning: test chains do not keep 10-minute blocks: the tip check and the dates are rough; check the tip by hand``, with no release advice and no `--accept-tip`. The line is printed on every run on a real testnet3 tip, since the anchor is the 2011 genesis block and a current tip is always years off it (only a tip within 180 days of the genesis block, which no card minted by this release can carry, draws nothing more than the tip line); `--accept-tip` is accepted there and changes nothing, because the check never refuses off mainnet and there is nothing to override. Signet keeps the check: its signed blocks are targeted at 10 minutes and the §7a rehearsal is built on its anchor, but whether a live signet tip stays within 180 days of that extrapolation was not checked against a node, so a signet tip may draw the mainnet text. When the tip's time is before the anchor's the second line reads ``the tip's time is N days before this release's anchor (2024-04-20): check `--time` `` in place of the anchor's age. On every network a tip no chain can have is refused, with no override: a height of 500,000,000 or more (`tip height … is not a block height: …`; from 500,000,000 an nLockTime is a unix time) or a time before the network's genesis block (`tip time … is before this network's genesis block …`), each naming `--height` and `--time`, since a swapped pair gives one; `export` only warns, and dates no height from such a tip (`warning: heights are printed without dates: this tip is not one a chain can have, so no date is estimated from it`). `member --for-spend` runs no tip check, so recovery is never blocked by it: it prints only the tip line. `export` has no `--accept-tip`, so its warning leaves out the advice to pass it |
| Numbers | Printed numbers carry thousands separators (`1,260,000`), except in script text, command lines, flag values, indexes, epochs and hex ids |
| Streams | Results go to stdout; warnings go to stderr as `warning: …`; errors print as `mr: <message>`. A reader that closes the pipe early (`mr decode --network testnet … \| head -1`) only stops the output: the exit code is the verb's own. Any other write error on stdout (a full disk, `> /dev/full`), from a verb or `--help`, prints `mr: cannot write the output: <error>` and exits 1. A stdout closed outright (`>&-`) behaves as `> /dev/null`: the output is discarded and the exit code is the verb's own |
| Printed placeholders | A placeholder `mr` prints in its own text (`MR1_CARD`, `THEIR_OWN_SEED`, `THEIR_KIT_MK1_PLATES`, `THEIR_KIT_SEAT_CHECKS`, `EXECUTOR_KIT_SEAT_CHECKS`, `HEIGHT`, `TIME`, `EPOCH`, `SLOT`, `INDEX`, `ADDRESS`, `LEAD`, `DESCRIPTOR`, `CARD`, and any other word of capitals, digits and `_` that holds a `_`; and the single letters `mr` prints for a number, `H`, `T`, `E`, `S` and `I`, each only as the whole value of the flag it is printed for: `--height H`, `--time T`, `--epoch E`, `--slot S`, `--index I`), pasted unchanged into the card (any of its strings), `--seeds`, `--keys`, `--lead`, `--funded-address`, `--witness-descriptor` or a numeric flag (`--height`, `--time`, `--epoch`, `--slot`, `--index`), is named and never read as input: ``mr: `MR1_CARD` is a placeholder from `mr`'s printed text: put the card's mr1 strings (a chunked card's strings in one pair of quotes) there``; for a seed ``… `THEIR_OWN_SEED` is a placeholder from `mr`'s printed text: put your seed's words or its ms1 plate, in quotes there``; for a key, ``… put the mk1 plates or `[fingerprint/path]xpub` records, each in quotes there``; for a seat-check placeholder (`THEIR_KIT_SEAT_CHECKS`, `EXECUTOR_KIT_SEAT_CHECKS`) wherever it is pasted (in place of a key, after `--seeds`, or in the card position), ``… `THEIR_KIT_SEAT_CHECKS` is a placeholder from `mr`'s printed text: in its place put the `--seat-check` arguments the kit notes or bag sheet give, each with its flag, or nothing when they give none``, since it stands for those flags, not for keys; for a file name (`--seat-lines` and `--keys-file`), ``… `THEIR_KIT_SEAT_LINES` is a placeholder from `mr`'s printed text: put the name of a file holding your kit's "seat key:" lines there`` (``… put the name of a file holding the mk1 plates or records there``), unless a file of that name exists, which is read; for a number, ``… put the number there`` (a usage error, exit 2; the card, seed and key refusals are exit 1). A bare listed word is a placeholder in `--seeds` only as that flag's lone value (seed words in capitals, unquoted, may include one, and get the split-words text instead); a placeholder with a `_` is named anywhere. No placeholder is a valid input, so no valid value is refused (an upper-case ms1, mk1 or mr1 string, seed words and numbers all pass), and a number out of range keeps its range text (`not in 0 … N`) |
| Secrets | `mr` never prints a private key, entropy or an ms1 seed string. It prints seed words in one case only: for each seed that `--seeds` gives as BIP-39 words, stderr carries `seed <n> read as <language>: <words>` once, so the words can be checked against the backup. Treat stderr as secret whenever `--seeds` holds words. A card argument that does not start `mr1` is never echoed: seed words (spaced or comma-joined), an ms1 string, an mk1 string or an md1 string is refused by every verb but `units`, which reads an md1 card (below), naming only what it looks like, e.g. `a card argument looks like seed words (<n> words, not echoed): seeds go in --seeds, and a card is its mr1 strings`. `member`, `address` and `current` refuse any other non-`mr1` value the same way, quoting only a bare integer of at most 20 digits (the `--epoch`/`--slot` hint); `units` reads a non-`mr1` argument as a template: one with no `(` is never a template and is never quoted, only named by its kind (an extended private key, a WIF or base58 key, hex, seed words joined by any punctuation, or a bare word), and a template's parse error names a bad part by its character, never quoting it. A usage error never echoes a value at all (a phrase typed without its verb, as a flag's value, or as the `<lang>` of `--seed-language 1=<lang>`): it names the value by its position, and keeps the verb and flag names as they are. The command line itself (shell history, the process list) is outside `mr`'s reach |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | refused or failed (a guardrail, a check, a key that does not fit; a value `mr` itself refuses after the parser has accepted it: a card string that does not decode, a slot the card lacks, an unreadable `--keys-file`, a `--template-preset` name, a value of a hot-family flag of the wrong form (`--hot-child`, `--first-hot-child`, `--retire-child`, `--bundle-account`, `--hot-on`, `--compromised`), a `verify --against` value that is not an md1 card; also a mandatory input `mr` checks itself and finds missing: `--delta-blocks`/`--delta-seconds`, `--anchor-height`/`--anchor-time`, a participant's `--role`, a `--sibling` answer, `--slots` or `--preset`) |
| `2` | usage error: one the argument parser finds (an unknown flag, a missing argument it requires, a value the parser itself finds of the wrong form or outside a flag's fixed choices, such as `--network bogus`, `--height abc`, a placeholder pasted into a numeric flag (`--height HEIGHT`) or an `--index` of `address` or `upgrade` above 2,147,483,647 (``not in 0 … 2,147,483,647 (an address index is an unhardened BIP 32 index)``); the hot-family flags above take free text, so their values are `mr`'s own check, exit 1), and the spec's closed list (§7 "Input and output"): no keys or seeds for a seat the Pubkeys TLV does not key, a malformed or repeated `@i=` binding, `verify --against` with an empty value, `--seed-language` or `--accept-seed-language` without `--seeds`, `create` or `upgrade` given no tip, and a seed, ms1, mk1 or md1 string typed where a card goes; also a missing tip in `member`, `address` or `current`; `mr repair`: nothing could be corrected |
| `5` | `mr repair` only: the strings were corrected |

A usage error's `Usage:` line is the verb's own, as `--help` prints it (`Usage: mr verify [OPTIONS] [mr1]...`), never clap's list of every flag the run gave as if each were required.

### Keys and seeds

`verify`, `member` and `address` take the set's keys in one of these
forms. On a card whose Pubkeys TLV keys every seat, `member`, `address`
and `export` need neither `--keys` nor `--seeds`: every key comes from
the card (`member --as policy` still needs a seed or plate for a seat,
since a signer registers only a key it holds). On a card with a seat it
does not key, `member` or `address` given neither is a usage error
(exit 2), and `export` refuses it (exit 1).

| Form | Meaning |
|---|---|
| `--keys <mk1…>` | an mk1 plate (a chunked plate's strings in one value, separated by spaces), typed as `mk encode` prints it and a plate engraves it or without its groups: each string's groups of characters separated by spaces, `-` or `,` (`mk1qp gylyp qqsqs …`) are joined to the string they follow, as mk-cli strips them; a value of groups alone (a grouped plate the shell split, typed unquoted) continues the string before it; and a chunked plate's strings given as values one after another (as the recipe's `--keys MK1_PLATES` invites), in any order, are one key while they are chunks of one set. A group is bech32 characters only, never a `1`, so an ms1 or mr1 string, a record or a word is never joined to a plate. A word after a complete plate is its own value, however its letters read: a string that already verifies takes no more groups, so `dave`, or the `seat` that an unquoted seat-key line begins with, is refused by itself (as seed words, or as a seat-key line to quote) and the plate before it reads. A lone value of 8 hex digits is refused as a fingerprint cut from its record: ``this value is 8 hex digits, a fingerprint on its own (not echoed): `--keys` takes mk1 plates or `[fingerprint/path]xpub` records, with the fingerprint inside the brackets``; a lone word as seed words, or a stray group of a plate: ``this value looks like seed words (1 word, not echoed): seeds go in `--seeds`, and `--keys` takes mk1 plates or `[fingerprint/path]xpub` records; if it is a stray group of an mk1 plate, give the whole plate, in quotes`` (on a `--keys-file` line, ``…, give the whole plate, its groups joined on one line``). A character outside the codex32 alphabet is refused with its string and its place counting `mk1`, from 1, with the plate's spaces and hyphens not counted: ``key 1, string 2 of 2: character 9 (counting `mk1`, not counting spaces or hyphens) is not in the codex32 alphabet (qpzry9x8gf2tvdw0s3jn54khce6mua7l; `b`, `i`, `o` and a `1` after the `mk1` never occur): check it against the plate``. A string of a chunked plate given without the plate's other strings is refused naming it: ``key <k>: string 1 of a 2-string mk1 plate, given without the plate's other strings: give every string of the plate: in `<flag>`, in one quoted value or as values one after another; in `--keys-file`, on the lines that follow it``, the `--keys-file` clause only when `<flag>` is `--keys` (`--sibling-keys` has no file). Every key text a value can draw names `<flag>`, the flag the value was given in: `--sibling-keys` for a value given there, `--keys` otherwise, a `--keys-file` line included |
| `--keys "[fp/path]xpub"` | a record: a key in `verify`; double-quote it (or write the path's `'` as `h`, still quoted in zsh, whose `[…]` is a glob): an unquoted `'` opens a shell quote in bash, zsh, sh and fish, so two records merge and lose their `'`s, which `mr` refuses with ``…; if a shell merged records, quote each record, or write the path with h: an unquoted `'` opens a shell quote (`<flag> "@0=[fp/270028'/1'/0']xpub"`, or `@0=[fp/270028h/1h/0h]xpub`)``; the record's xpub must be at its path, its depth the path's length and its child number the path's last step (as `mk encode` requires), in every verb that reads one: ``key <k>: the record's xpub is at depth 3, child 0', not at m/270028'/1'/1' (depth 3, child 1'): the device exported another path; ## `mr verify`

Re-read an engraved card and check it against ids, keys or seeds. With
keys or seeds it prints the seat each one filled (`plate 2 → seat @2,
sc:…`; a device record's line, `record 3 → seat @1, sc:…`; the plates that
filled a seat by then are listed before a refusal too), and for
each seed the seat it filled or agreed with, ending with that seat's
seat check (`seed 1 → seat @0, sc:…`, `seed 2 → seat @1 (agrees with
plate 2), sc:…`, `seed 1 → seat @2 (its child 24/0), sc:…`; a seed given
twice, or the hot child's own words beside its parent, agrees with what
filled the seat: `seed 3 → seat @1 (agrees with seed 2), sc:…`, `seed 3
→ seat @0 (agrees with seed 1's child 24/0), sc:…`; a seed refused at its
seat, or a run that fails a card rule, prints none), followed by ``your
seats' seat checks are printed for comparison where a kit asks for them;
never keep them beside your seed: with the seed they test the
passphrase``, and fails on a stub mismatch or a seed that
fills no seat (see Keys and seeds). A seat check covers every seat's key
(below), so a run that holds no key for some seat prints none, and says
once, on stderr, ``no seat check printed: seat @2 has no key in this run,
and a seat check covers every seat's key`` (``seats @1 and @2 have``); a
`verify` of the card alone prints the keyed seats' checks (``seat @0
(keyed by the card): sc:…``) only on a fully keyed card. On a stub mismatch it says ``…: re-mint
that plate before engraving``, unless the plate's fingerprint is none
this card declares either: then ``…: a plate of another card, or minted
wrong: plate <k> looks like another card's plate (stub <s>, fp <fp>):
check that you hold this card's kit; re-mint a plate only if it is this
card's`` (`export` warns the same `plate <k> looks like another card's
plate …` line beside its stub warning, and goes on; `member` and
`address` refuse it with the same words, ending ``…; if it is this
card's, pass `--accept-stub-mismatch` to `mr <verb>` to use them``,
"to use it" when the refusal names one plate).
A plate matches when it carries the card's (0, 0) stub: the template id
on a keyless card; on a keyed card its `WalletPolicyId`, the stub
`create`, `upgrade` and `decode` print for minting (``(0, 0) stub: 0aeaa2ea (the `--policy-id-stub 0aeaa2ea` of every `mk encode` line)``), or its template id,
which a plate minted from the keyless md1 of the same wallet carries
(this second form is a default the owner may still change). On a keyed
card every stub text names both forms (``its (0, 0) stub is <policy>
(the `WalletPolicyId`) or <template> (the template id); plate 2 carries
…``), as does the warning `--accept-stub-mismatch` prints in `create`,
`upgrade`, `member` and `address`.

A seed no key confirms is refused naming the seats, singular or plural:
``seat @1 is not confirmed: give its device record or mk1 plate with `--keys`, or your kit notes' `--seat-check` values``
(``seats @0, @1 are not confirmed: give their device records or mk1 plates
with `--keys`, or your kit notes' `--seat-check` values``; with no key at all, the warning ``seeds not confirmed against any key: add `--keys RECORDS_OR_PLATES` or your kit notes' `--seat-check` values``). On a card with no fingerprints a seed confirms no seat, so the refusal names where each device record comes from, "seat @1 is not confirmed: give its device record, exported at m/270028'/1'/1', or mk1 plate with `--keys`, or your kit notes' `--seat-check` values" ("…: give their device records, exported at m/270028'/1'/0' and m/270028'/1'/1', or mk1 plates with `--keys`, or your kit notes' `--seat-check` values").

A plate never confirms by itself a seat that nothing on the card ties to
this wallet. A keyless card's (0, 0) stub is its template id, which
every card of that template shares, and a keyed card accepts that stub
too (§9 Q40), so another wallet's plate of the same template at a seat's
path fills the seat. A seat is untied when the card keys no xpub for it,
whatever fingerprint it declares there, and a record or a plate alone
fills it, whatever stub the plate carries, with no given seed deriving
its key and no funded witness: a declared fingerprint confirms a seed
that has it, never a plate's or record's key, since it is a 4-byte label
any plate or record can carry. A keyed card's `WalletPolicyId` does not tie such a seat
either: it hashes only that seat's path, which every card of the
template shares, so two partly keyed cards without fingerprints that
key the same seats print one stub. Such a seat is reported ``seat @1:
filled by plate 2, sc:… (nothing on this card ties this key to this
wallet: give the `--seat-check` value your kit notes or bag sheet give
for set <id>, seat @1, or compare this seat check with the seat holder's
before any deposit)`` (``record 1`` when a record fills it, in `verify`), never
"confirmed by", in `verify`, `member`, `address`, `member --for-spend`,
`export` and the heir file. `verify` exits 0 and ends ``verify: passed,
but seat @1 is only filled: nothing on this card ties its key to this
wallet; compare its seat check with its holder's, and give your kit
notes' `--seat-check` value for it, or, for an extra plate, the value on
its label (if they give none, the value `mr
verify` with that seat's seed prints on its seed line, or on its device
record's line; for a sealed or executor-mode heir's seat, the seat check
printed by `mr verify MR1_CARD --seeds KIT_SEEDS --keys KIT_PLATES
"HEIR_RECORD"` (HEIR_RECORD the record form of the xpub on the heir's
seat-key line, brought from the heir's kit, and KIT_SEEDS and KIT_PLATES
this kit's seeds and plates), or re-minted kit notes; a line with no fingerprint, on a card made with `--no-fingerprints`, gives the record `[00000000/PATH]XPUB`, 00000000 standing for the missing fingerprint)`` (for several,
``verify: passed, but seats @0, @2 are only filled: nothing on this card
ties their keys to this wallet; compare their seat checks with their
holders', and give your kit notes' `--seat-check` values for them, or, for
extra plates, the values on their labels (if
they give none, the values `mr verify` with those seats' seeds prints on
their seed lines, or on their device records' lines; …)``). A seat whose
given seed agrees with its plate stays confirmed, by the seed: ``confirmed by seed 2 (plate 2 agrees)``. A card
with fingerprints refuses a plate that carries another fingerprint (see
above), but one carrying the card's own is only filled, like any other.
In `export` and `member --for-spend` such a seat whose plate carries
another fingerprint, or none on a card that declares one, is reported
``seat @1: filled by plate 2, sc:… (fingerprint-disputed: compare this
seat check with the seat holder's)``, and, tied by a matching value,
``seat @1: filled by plate 2, tied by `--seat-check` (fingerprint-disputed)``.
A plate bound to a seat with `@i=` in `export` or `member --for-spend` is
reported the same way, ``filled by plate 2, sc:…``, never "confirmed".
`export` prints each plate of an undecided group at such a seat, ``plate
2: undecided (nothing on this card ties this key to this wallet)``, with
no seat check: the plate has a seat, and so a seat check, only once a
seating places it (``no seat check printed: seats @0 and @1 are
undecided, and a seat check covers every seat's key``).

**The seat check** is `sc:` and 32 hex digits in eight groups of four, a
key half and a wallet half of 16 digits each. The key half is the first 8
bytes of SHA-256 over `mr1/sc-key`, the card's set id (8 bytes), the seat
number (1 byte) and that seat's chain code and compressed key; the wallet
half the first 8 bytes of SHA-256 over `mr1/sc-wallet`, the set id, the
seat number, the card's seat count (1 byte) and every seat's chain code
and key in seat order, each the key that fills it in the run (the card's
xpub at a keyed seat). Every card of one template can share a set id, so
the wallet half is what ties a value to this wallet's keys; the key half
says which seat's key differs. Two values compared: both halves equal,
the same keys at every seat; the key half different, a different key at
this seat, or another seat's or card's value; the key half equal and the
wallet half different, a different key at another seat, or a value made
for another wallet of the template. Test vectors: a card of three seats,
set id `17df92c526428c7b`, holding BIP 32 test vectors 1, 2 and 3's
master keys, gives `sc:fe28-2294-e1d5-c4f0-146d-9d55-9651-902f`,
`sc:5d5a-945b-d8e7-459d-a7ff-0c47-ac45-da99` and
`sc:47a4-fda6-7e26-fb8d-ae6a-0285-b6d3-94f9`. Whoever holds the other
seats' keys can compute a value for a key of their own, so only the
comparison with each seat holder's own value catches a forged key.

**`--seat-check [<set-id>:]@<i>=sc:<32 hex>`** (`verify`, `member`,
`address`, `export`, repeatable) gives a seat's seat check as its holder
compared it, the value the kit notes give (``set <id>, seat @1's seat
check: `--seat-check <id>:@1=sc:…` (give it to every `mr member`, `mr
address`, `mr verify` and `mr export`; compare it with the seat holder's
before the first deposit)``). The set id, full or its 8-hex-digit
prefix, names the card; it may be left out on a run given one card. A
matching value ties an untied seat for the run (``seat @1: filled by
plate 2, tied by `--seat-check` ``); when every such seat is tied,
`verify` ends ``verify: passed``. A value that differs, at any filled
seat, is refused by the half that differs, the value named by its
position, never quoted. When its key half differs: ``seat @1: plate 2
has sc:…, not `--seat-check` value 1: its key half differs, so this
seat's key is not the one the value was made from, or the value is
another seat's or another card's (or this card's on another network);
check the value against the seat holder's (and the plate against its
label)`` (``(and the record against
its device)``, ``seed 1 has … (and the seed's passphrase)``, ``the
card's xpub has … (the card keys this seat: the value is wrong)``, which
`verify` also gives with no keys or seeds on a fully keyed card), and
`member --for-spend`, and `export` with a single candidate seating, add
``; or leave the value out: this verb runs without it``. When only the
wallet half differs: ``seat @1: this run's keys give sc:…, not
`--seat-check` value 1: the key half matches, but a key differs at
another seat, or the value was made for another wallet of this template,
or it was copied wrong[; no value given here names seat @2 (plate 2): a
wrong seed or passphrase there, or another key there than the one the
value was made with, would also do this]; compare each seat's value with
its holder's, and look for the seat whose key half differs; if none does,
do not deposit until each holder's full value matches``, the bracket
naming each seat no given value names (``seats @0 and @2 (seed 1 and
plate 2)`` for several), as causes only: it names nothing as wrong and
offers no "leave the value out". A value that equals in both halves the
seat check another seat has in this run is that seat's, given under the
wrong seat: ``seat @1: `--seat-check` value 1 is seat @0's seat check, not
seat @1's: give it as`` `@0=` (the message ends with that binding). A run prints every key-half refusal, and the wallet-half ones only
when no key half differs. On a run with no key for some seat a value
checks nothing: `` `--seat-check` value 1 checks nothing: seat @2 has no
key in this run``. In `export`, where several candidate seatings are
tried (`--try-seatings`, an undecided plate group), the values are
checked against each, the ones they differ at are dropped and counted on
stderr (`` `--seat-check`: 5 of 6 candidate seatings dropped: a value
differs``), and the run refuses only when none is left: ``
`--seat-check`: all 6 candidate seatings dropped: no seating of the
given plates gives these values; they were made for another wallet, or a
plate is not this wallet's; compare each seat's value with its
holder's``, followed by ``; or leave the value out: this verb runs
without it`` when every dropped seating differs in a key half, and
otherwise by ``; some seating matches every given key half, so a key at
another seat may be forged: do not deposit until each holder's full
value matches``. When every candidate leaves a seat without a key, no value
can be checked, and each is ignored with a ``checks nothing`` warning, once:
the first form above (`` `--seat-check` value 1 checks nothing: seat @2 has
no key in this run``) for a value on a run that holds no key for some seat,
or, for a value whose own seat no kept candidate fills, the other
(``seat @2: nothing fills it, so `--seat-check` value 1 checks nothing``).
A value of 20 hex digits, the form of kit notes printed
before this release, is never compared: naming a given card it is
refused at any seat, before the other checks below, ``mr:
`--seat-check` value 1 is a seat check in a former form (20 hex digits):
re-print your kit notes from the kit's re-mint note (`create` or
`upgrade` again, which gives the same card), and give the new value``
(`export` and `member --for-spend` adding ``; or leave the value out:
this verb runs without it``); naming no given card it is warned of,
``…is a seat check in a former form and names no card given here:
re-print that card's kit notes from its kit's re-mint note``. The seat
takes no leading zero (`@01=` is not of the form). A value that does not read, a
second value for one seat of one card (``a second value for one seat``),
or a value with no set id on a run of several cards (``give each value
its card's set id, since this run has several cards``) is a usage
error, exit 2, never echoed: ``invalid value for '--seat-check
<[SET_ID:]@I=sc:HEX>' at position <n> (not echoed): it takes the card's
set id and a colon (optional on a run of one card), then @<i>=sc: and
the seat check's 32 hex digits, as your kit notes give them``. Once the
card is read, a seat it lacks is refused, ``mr: `--seat-check` value 2:
the card has no seat @7``, as is a set id prefix two given cards share
(``mr: `--seat-check` value 1: its set id prefix is that of cards <id>
and <id>: give the full set id``). A value for a seat nothing fills
warns ``seat @1: nothing fills it, so `--seat-check` value 1 checks
nothing``, and one naming no given card warns `` `--seat-check` value 1
names no card given here, so it checks nothing``. A value that matches in
both halves covers every seat's key, so it confirms each seat a given seed
(or that seed's hot child) fills that nothing else confirms, reported
``seat @0: confirmed by `--seat-check` value 1`` (the first such value
names it): `member` and `address` hand out, and `verify` passes, with the
kit notes' values alone on a card with no fingerprints. A seat a plate or
record fills still needs its own value, and with no value a seed stays
unconfirmed: `--accept-unconfirmed-seeds` stays the seeds' consent.

`member` and `address` refuse an untied seat that no `--seat-check`
ties, exit 1, one line per such seat, then the seat check of each seat
a given seed fills and, when there is one, the keep-apart note:
``seat @1: filled by plate 2, but nothing on this card ties this key to
this wallet: give the `--seat-check` value your kit notes give for set
<id>, seat @1 (for an extra plate, the value on its label); if seat @1 is your own seed's, give the seed with
`--seeds`, which ties it; otherwise, if the kit notes give no seat check
for seat @1 nor for any other seat of set <id>, they predate seat checks:
re-print them from the kit's re-mint note (`create` or `upgrade` again,
which gives the same card); if they give none for this seat only, compare
this plate's seat check, sc:…, with the seat holder's, and give the
holder's (for a sealed or executor-mode heir's seat, which prints none:
give the record form of the xpub on the heir's seat-key line, brought
from the heir's kit, as HEIR_RECORD, with KIT_SEEDS and KIT_PLATES this
kit's seeds and plates, to `mr verify MR1_CARD --seeds KIT_SEEDS --keys
KIT_PLATES "HEIR_RECORD"` and read the seat check it prints, or re-mint
the kit notes; a line with no fingerprint, on a card made with `--no-fingerprints`, gives the record `[00000000/PATH]XPUB`, 00000000 standing for the missing fingerprint)``, ``seat @0:
filled by seed 1, sc:…``, ``your seats' seat checks are printed for
comparison where a kit asks for them; never keep them beside your seed:
with the seed they test the passphrase``. A run with an untied seat and
an unconfirmed seed-filled seat is refused once, the untied lines first,
then ``seat @0 is unconfirmed: nothing on this card checks its seed; give
its plate or device records, or your kit notes' `--seat-check` values, or
pass`` `--accept-unconfirmed-seeds` (the message ends with that flag), since the values tie the plates and,
matching in both halves, confirm the seeds; `--accept-unconfirmed-seeds`
lifts only that half and does not lift the untied seats' refusal. `export` and `member --for-spend` print the filled
line and do not refuse; `member --for-spend` refuses a differing value,
and `export` drops the seatings it differs at (above).

`--set-id` and `--digest` take the full 16 hex digits; any other length,
such as `export`'s 8-digit `[card …]` prefix, is a usage error (exit 2)
that says so and does not quote the value (for `--digest` it adds that
`export`'s `[card …]` shows only the first 8). A full-length value that is the
card's other id is named, and the card is not called another set: `--set-id`
given the card digest fails ``the set id is <id>, not <value>: <value> is
this card's digest, not its set id: give it with `--digest` ``, and
`--digest` given the set id the reverse (``the card digest is <digest>, not
<value>: <value> is this card's set id, not its digest: give it with
`--set-id` ``); any other value fails ``…: this card is not that set``
(``…: this is not that engraving``). `--against` compares like
with like: when both cards carry xpubs and fingerprints at the same
seats, their policy ids, which cover every seat's origin path,
fingerprint and xpub (``(0, 0) matches the md1 card``); otherwise (two
keyless cards, one card keyed and the other not, keys at different
seats, or one without fingerprints) the template ids, then each seat by
its xpubs where both carry one, else by the fingerprints both declare
(``member (0, 0) does not match the md1 card at seat @<i>: its
fingerprint is <fp>, the md1 card's <fp>``) and their origin paths,
since the same seed at another path is another wallet (``member (0, 0)
does not match the md1 card at seat @<i>: its origin path is <path>,
the md1 card's <path> (the same seed at another path is another
wallet)``; this is checked on every seat the two cards do not key
identically, every seat of two keyless cards, one with neither an xpub
nor a fingerprint on either side included). The first seat that differs
is named, xpubs and fingerprints before origin paths, and no xpub is
echoed. It is not a byte comparison: a card `upgrade` issued with
fingerprints it added passes against its fingerprint-less md1. A pass
between two keyless cards prints ``(0, 0) matches the md1 card: the
same template, and each seat's origin path, and its fingerprint where
both declare one``; a pass across forms prints ``(0, 0) matches the md1
card: the same template, and each seat's xpub where both carry one, else
its fingerprint, and its origin path (the two carry xpubs or
fingerprints at different seats)``. Where the md1 card carries an xpub at a seat and this card none, a key the
run seats there (a seed's, a hot child's, a plate's or a record's) is
compared with it, chain code and key alone: a difference is refused,
``member (0, 0) does not match the md1 card at seat @0: the key this run
seats there is not the md1 card's xpub``, and a match counts as compared
by xpub (a forged upgrade's plates, which carry the right fingerprints,
passed "by fingerprint only" while the run held every seat's key; on a
card without fingerprints the owner's own keys were refused as not
comparable). A seat the run holds no key for is compared by its
fingerprint alone, or, with none, refused as below. When no seat has a fingerprint or an
xpub on both cards, so that any wallet of the template would match, the
run ends ``verify: passed, but the md1 card was compared by template and
origin paths only: no seat has a fingerprint or xpub on both sides, so
any wallet of this template matches`` in place of the bare pass. When the
md1 card's xpub at a seat was compared by fingerprint alone, since this
card carries none there, the run ends
``verify: passed, but the md1 card was compared at seat @1 by fingerprint
only: the md1 card's xpub there is not checked, since this card carries
none; compare that seat's seat check with its holder's`` (``at seats
@0, @1 and @2 … the md1 card's xpubs there are not checked … compare
those seats' seat checks with their holders'``): a forged md1 with the
right fingerprints and another wallet's xpubs passes such a compare. The
line names those seats even when another seat was compared by xpub: on a
card that keys only seat @0, a forged md1 with the right xpub at @0 and
another wallet's at @1 and @2 ends ``… compared at seats @1 and @2 by
fingerprint only …``, and so does the honest md1, since the run cannot
tell them apart (this goes beyond the spec's "When no seat was compared
by xpub", a spec-thread item). Two cards that carry no xpub keep the bare
pass after a fingerprint compare.
When the run also ends with an untied seat's line, that line stays last
and either text is printed before it as a warning (``warning: the md1
card was compared by template and origin paths only: …``). The parentage
form (`--hot-record`) prints either text as a warning too, before its
own pass line. A seat one card keys that the other
neither keys nor declares a fingerprint for is refused, not passed:
``member (0, 0) cannot be compared with the md1 card at seat @<i>: the
md1 card carries its xpub, and this card neither keys it nor declares
its fingerprint``.

**Seat-key lines, no card.** `mr verify --network <net> --seat-lines
<lines> --seeds …` is the check of an heir whose card is sealed or with
an executor (see `mr create`, Heir card modes): it reads no card and
checks the heir's own seeds against the "seat key:" lines in their kit
notes (`seat key: seat @2 (letter C): origin path m/270028'/1'/2', xpub
tpub…, fingerprint 6d4a0b8f`; the hot seat's `seat key: seat @1 (hot
child 24/0 of seed A, letter K): …`). `<lines>` is a file (read up to 1
MiB; a larger one is refused), or the text itself when no file of that
name exists; only lines that begin "seat key:" are read, so the whole
kit notes may be given, and with none it fails ``no seat-key line
given`` (for a value that is no file, ``no seat-key line given: `--seat-lines`
names no file that exists here, and its value holds no line that begins "seat
key:"; check the file name``; for an existing file with no such line, ``no seat-key line given: the
file `--seat-lines` names holds no line that begins "seat key:"; only a sealed or executor-mode
heir's kit notes carry them: with the card, check a seed with `mr verify MR1_CARD
--network N --seeds "THEIR_SEEDS" --keys "KEY_1" "KEY_2"`, KEY_1, KEY_2 and so on the plates of
the seats those seeds do not fill``). Every printed command quotes it, `--seat-lines
"THEIR_KIT_SEAT_LINES"`: a seat-key line holds spaces, `(` and a `'`,
which unquoted end the command or open a shell quote; a file name (the
kit notes saved as a file) is the safer value, since lines pasted onto
one line are not read as several. For each line it takes the given seed of the line's letter (for
the hot seat, the hot child's own words, of the child's letter); when
two given seeds have that letter, the line's fingerprint picks one, and
without a fingerprint the line passes when either agrees. It derives the
xpub at the line's origin path and prints ``seed <n> → seat @<i> (agrees
with its seat-key line)``; it fails on ``seat @<i>: seed <n> derives
another xpub: a wrong seed or passphrase, or a line copied wrong (`verify`
takes no passphrase: if your seed has one, compare the xpub your signer shows at
the line's origin path with the line)``, ``seat @<i>, letter <L>: no given seed
has this letter; give this kit's own seed for this letter (its ms1 plate is
labelled <L>)`` (when a given seed has the line's fingerprint and derives its xpub, whatever its letter, it says so instead: ``…no given seed has this letter; seed <n> (letter <M>) has the line's fingerprint and derives its xpub: the card, or this copy of its line, gives seat @<i> the wrong letter <L>, and that seed's letter is <M>: `mr decode MR1_CARD` with this run's `--network` prints the card's seat map (MR1_CARD the card's strings; a sealed heir's card stays in its bag: ask the creator); if the card gives seat @<i> letter <L>, the creator mints the card again with `--seat-map` giving that seat letter <M> (and that seat holder's `--role` with letter <M>), and replaces it in every kit before any deposit; if it gives <M>, this copy of the line is mistyped: give the line as the kit prints it``; on a line with no fingerprint, ``seed <n> (letter <M>) derives the line's xpub``) (for the hot seat: ``…; seat @<i> is a hot child: give the hot
child's own words (from its ms1 plate in your kit), not its parent seed's``), a
fingerprint the line gives that no seed of its letter has (with the same
passphrase sentence), and an xpub or an origin-path coin type of another
network than `--network` (``…: give the network of the kit's card (a kit with
no card, an executor-mode heir's, names it on its `network:` line)``); these come
first, over every line, and then a line that no given seed agrees with
fails once for the seed its fingerprint picks, or, without one, once per
seed of its letter. A given seed that agrees with no line, whatever its
letter, is skipped, not failed, with ``seed <n> (letter <L>) agrees with
no seat-key line: not checked here; if it is one of your kit's seat
seeds, a seat-key line is missing`` on stdout: the lines list only the
kit's seats, so a missing line is the one case this check cannot see,
and the card form (with the whole card) is where a stray seed is
refused. A passing run ends ``verify: passed for the seeds these lines
name``. A line that begins "seat key:" but does not read as one is named by its
number, never quoted, with the part that fails (``its xpub does not read (a
character copied wrong; its checksum fails): compare it with the kit notes,
character by character``; the origin path, the seat number against the path,
the fingerprint, the letter and the hot-child words are named the same way); so is one whose seat number differs from its
origin path's (a path of the form `m/270028'/<coin>'/<32r + i>'` names seat
i) or whose hot-child words do not read "hot child \<len\>/\<i\> of seed
\<P\>, letter \<C\>". A seed plate whose language is not recorded is
searched as the card form searches it, with the line's fingerprint in
place of the card's, or on a line without one its xpub (see Keys and
seeds). A card, `--keys`, `--keys-file`, `--digest`, `--set-id` or
`--against` given with `--seat-lines` is refused (exit 1), with the
message ``` `--seat-lines` reads no card: give it with `--seeds`
alone ```. It proves the heir's seeds, not the card, which the creator's
own `mr verify` proved before sealing the bag. While `mr verify` takes
no passphrase, the holder of a seed with one leaves it out and compares
the xpub their signer shows at each line's origin path with that line.

**Parentage form.** `mr verify <mr1> --network <net> --hot-record
<L>/<len>/<i>[=<word>] --hot-key <record> … --hot-parent-passphrase
yes|no [--hot-parent-fp <fp>] --seeds … [--passphrase <n>=…]` is the closing sitting's check
of a hot child minted from its public record (see `mr create`, Minting
from the hot child's public record): `create` prints this command in its
closing checklist with the record's values filled in. It takes the card,
the mint's record (the hot child's one `--hot-record` value, its word 1
optional, and no tried values; its `--hot-key` records at the paths the
mint required, one at another path refused), the history inputs as the
mint was given them (`--sibling` and `--bundle-card`, each with its
`--sibling-keys`, `--retire-child`, `--compromised`,
`--first-hot-child`, `--hot-on`), and seed L with every other seed your
role lists that has no passphrase of its own (a seed with its own
passphrase is given by its seat's plate or record in `--keys`).
With `--hot-parent-passphrase yes`, seed L's passphrase is asked for on
stdin, twice, with the echo off on a terminal (a pipe or file is read as
it is): ``seed <L>'s passphrase, the hot child's parent's:``, then
``seed <L>'s passphrase, typed a second time:``. Two answers that differ
(one empty and one not included) are refused, ``seed <L>'s passphrase,
typed a second time, differs from the first: give it again``; end of
input at either answer is refused, ``seed <L>'s passphrase was asked for
on stdin, and none was given``; two empty answers are seed L without a
passphrase, refused by step 1's `--hot-parent-passphrase` text. In its
place, `--passphrase <n>=PASSPHRASE` gives it, `<n>` seed L's input
position in `--seeds` or its letter, as `create` takes a seed's (it stays
in the shell's history); a parent that fills no seat of the card is then
asked once more, ``seed <L>, the hot child's parent, fills no seat, so
nothing on the card checks its passphrase: type it again:``, refused on a
differing answer or end of input with the texts above, and never asked a
third time; it is asked only with a value that is not empty and
`--hot-parent-passphrase yes`. With `--hot-parent-passphrase no`, a
`--passphrase` value for seed L that is not empty is refused by step 1's
`--hot-parent-passphrase` text and nothing is asked (nothing is read from
stdin); an empty value is seed L without a passphrase, as two empty
answers are, so it passes that check with `no` and is refused by its
text with `yes`, nothing asked. The form takes seed L's passphrase only: a `--passphrase`
for another seed is refused before any question, ``` `--passphrase` names
seed <n>, not seed <L>: the parentage form takes seed <L>'s passphrase
only; give a seed that has a passphrase by its seat's plate or record in
`--keys`, not in `--seeds` ```. The question comes after every refusal
that needs no answer: `--against`'s check, a card with no child entry
(``this card has no child entry: the parentage form checks the hot child
a card names``), a `--passphrase` for another seed, and step 1's
`--hot-key` paths and seed L checks. `--against <md1>` gives, for a card an `upgrade` with `--hot`
minted, the md1 it upgraded; its own (0, 0) check runs first, in its
card-form texts, so a wrong md1 is refused before anything else. These
flags without `--hot-record` (`--passphrase` and `--sibling-keys`
among them), a second `--hot-record`, a malformed or
repeated `--hot-parent-fp`, and `--hot-record` beside `--digest` or
`--set-id` are usage errors (exit 2); `--seat-lines` beside it is refused
as beside a card (exit 1); every refusal below exits 1. In this order:

1. The `--hot-key` paths, as `create`'s check (d) takes them (a record at
   a path the record does not use is refused, ``` `--hot-key` record <n> is
   at <path>, a path the record does not use: give the hot child's records
   at <paths> only ```; a path with no record is refused, ``` `--hot-key`
   has no record at <path>: give the hot child's record at each of <paths> ```);
   then seed L: ``seed <L>, the hot child's parent, must be given once in
   `--seeds`: the child's own words prove no parentage``; then its
   passphrase (above); ```
   `--hot-parent-passphrase <yes|no>` does not match seed <L> as given
   here (<with|without> a passphrase): give seed <L> as the child was
   made from it ```. A seat of letter L (not the hot seat) whose known
   fingerprint is not seed L's: ``seed <L> as given here has master
   fingerprint <fp′>, not <fp>, which seat @<j> carries: first check seed
   <L> and its passphrase as typed here; if they are right, another seed
   of letter <L> fills seat @<j>, and the hot entry names its parent by
   letter: before any deposit, choose a parent whose letter no other seed
   has, mint again and engrave again``. With `--hot-parent-fp`, a seed L
   whose fingerprint is not the field's: ```
   `--hot-parent-fp <fp>` was mistyped here: seed <L> as given has master
   fingerprint <fp′>, which seat @<j> carries: rerun this check with
   `--hot-parent-fp <fp′>` or without it ``` when a seat of letter L
   carries seed L's fingerprint, else ``seed <L> as given here has master
   fingerprint <fp′>, not `--hot-parent-fp <fp>`: first check seed <L>
   and its passphrase as typed here; if they are right, the field was
   mistyped here or at the mint, and the card does not carry it: rerun
   this check with `--hot-parent-fp <fp′>` or without it``. A given card's seat of letter L whose real fingerprint is not seed L's, when seed L was given with no passphrase, is warned of and not refused (a given card may hold another seed of that letter), as seed-mode `create` warns, unless seed L as given fills a seat of this card, which proves it is seed L: ``seed <L> as given here, with no passphrase, has master fingerprint <fp>, but set <id>'s seat @<j> has letter <L> with fingerprint <fp′>: if that is seed <L>, its passphrase is missing, and the fingerprint this run prints for seed <L> is not the one to keep; give seed <L> with its passphrase``. A seat of
   letter L whose fingerprint nothing here gives is checked by seed L's

   <path> is not its key: another seed of letter <L>, or seed <L> with
   another passphrase, fills it, and the hot entry names its parent by
   letter: before any deposit, choose a parent whose letter no other seed
   has, mint again and engrave again``, or, with no key for it, ``seat
   @<j> has letter <L> and no fingerprint: give its plate or record in

2. The record and the derived child: ``the record names child
   <L′>/<len′>/<i′>, but this card's child entry is <L>/<len>/<i>: give

   when the search would have taken a lower index j, ``with seed <L>, the

   take child <len>/<j>, not the md1's hot child <len>/<i>: an `upgrade`
   from seed <L> refuses this md1 too: move its funds with `create` ``;
   and, when the search would pass over the index, ``with seed <L>, this
   mint is refused: the search passes over child <len>/<i>, whose letter
   is not free on this card; …``.
5. The checks that need seed L (the BIP-85 children rule, seed L not a
   child of another given seed, the hot/cold guardrail on the given

master fingerprint <fp>, hot seat key and four accounts match; BIP 86
first address <addr86>`` (on a card with no hot seat, ``…, master
fingerprint <fp> and four accounts match; …``), for a parent that fills

run warns that a given card's seat of letter \<L\> carries another fingerprint),
and last ``verify: passed for
hot child <len>/<i>'s parentage``. It checks the parentage only: the card
form, run at the same sitting, checks the card and the kit. The card
form takes no passphrase yet.

## `mr decode`

Print everything an mr1 card holds: the template, delta and anchors,
set id, card digest, the (0, 0) policy id, stub and md1 card (as md1
chunks when it is over 80 symbols), the seat map, each seat's master
fingerprint from the Fingerprints TLV ("seat fingerprints: …"; "@i
none" for a seat the TLV leaves out, "@i none (00000000)" for one it
declares `00000000`, and "none" when the card has no Fingerprints TLV; the check §7a's lost-device
recipe asks for), each seat's origin path with its round when the paths are on the
convention (``seat origin paths: @0 m/270028'/1'/32' (round 1), @1 …``), the units (marked as `mr units` marks them, the P2WSH and P2SH script-size marks and the bare `sh()` mark included), each slot
(its locks, what it removes and drops, whether it is open or a
lock-up), the set end, each slot's deadlines at epoch 0, and a bundle
checklist when the card lists other cards. On a card with a hot child it names the hot seat (``@3 is the hot seat (child 24/0 of seed A, letter K)``). It also prints the network the card is read on (``network: testnet, coin type 1``, as `member` does). Heights are dated from the anchor on mainnet and, roughly, on signet (``the dates are rough, since test chains do not keep 10-minute blocks``); on testnet and regtest they stay undated and one line says why. One chunk of a chunked card is refused as `repair` words it (``this string is chunk 0 of a 9-chunk card (chunks are numbered from 0), not a card on its own: chunks 1-8 are missing; give all 9 chunks together``). It takes no keys.

### Synopsis

```sh
mr decode [OPTIONS] <mr1>...
```

| `--network <NETWORK>` | Network: main (default; `mainnet` is accepted too), signet, testnet or regtest [default: main] |

## `mr repair`

Correct up to 4 substituted characters per mr1 string. A chunk set is
repaired as one card, atomically: one uncorrectable string fails the
whole call with no output. A mixed-case string, and a string over 93
symbols after `mr1`, are refused before any correction. Exit `0`:
nothing to correct; `5`: corrected (a repair report and the corrected
strings on stdout); `2`: not correctable.

It then reads the strings as `decode` would and says on stderr what
they are. A card: "the repaired card decodes: set id …, card digest
…" and the next step, "next: check it against the digest recorded for
this card, then engrave the corrected characters: `mr verify <the
strings> --network NETWORK --digest DIGEST`" (NETWORK is the
`--network` you typed, when you typed one; replace each word in
capitals). One chunk of a chunked card: "this string is chunk 0 of a
9-chunk card (chunks are numbered from 0), not a card on its own:
chunks 1-8 are missing; give all 9 chunks to one `mr repair` call".
Strings that pass the checksum but are no card: "the corrected string
passes the checksum but is not a card (…): check it character by
character against the engraving", since more than 4 errors can be
corrected to another valid string. A string refused at the purpose number
(a wrong number, a non-minimal varint, or a header that ends inside that
field, whose refusal now carries the sentence in every verb: ``the card
header ends inside its purpose number field; a card a pre-release build
minted …``) is a pre-release card or a damaged one, never an engraving to
check: the warning ends after the refusal, which carries the re-mint
sentence of `decode`, with no "check it character by character" clause, and when repair changed characters it adds only the
caveat (``: `mr repair` corrects up to 4 substitutions per string, and a
string with more errors can be corrected to another valid string``). The
exit code is the checksum's either way.

The report counts strings and positions from 0, and a position is a character after the `mr1` ("mr1 string 1: 1 correction at position 7" is the eighth character after `mr1` of the second string); when something was corrected, stderr adds ``note: string numbers and positions count from 0; a position is a character after the `mr1` ``.

Every refusal that names an `mr1` string counts the strings from 0, as `repair`'s report does, and says so once beside a string above 0 (inside `mr repair` itself the note reads `(strings count from 0)`, with no pointer to the verb it is in) (this concerns `mr1` strings only: an mk1 plate's strings are counted from 1 in the plate refusals, which name the key and the string, as in ``key 1, string 1 of 2: the mk1 checksum does not verify``): ``string 1 (strings count from 0, as in `mr repair`): the mr1 checksum does not verify``. The chunk-set refusals follow it: ``string 1 (strings count from 0, as in `mr repair`) is of the chunk set that begins `mr1lzw2a`, but string 0 of the set that begins `mr1lzw2u`: these strings are not one card`` (a chunk set is named by how its strings begin: `mr1l` and four symbols, as engraved, not by a hex id), ``string 2 (strings count from 0, as in `mr repair`) says the card has 5 chunks, but string 0 says 4``, and a repeated chunk with a gap ``chunk 1 is given twice and chunk 0 not at all: give all 2 chunks of the card, each once (chunks are numbered from 0)``. A lone `mr1` argument (a space after `mr1` split the string) is ``string 0 is `mr1` alone: a space after mr1 splits the string; give the string without that space, or quote it whole``. `mr repair` of an mk1, ms1 or md1 string points to `mk repair`, `ms repair --ms1` or `md repair`.

`repair` corrects substitutions only. A string it cannot correct is
refused with "more than 4 substitutions, or a character left out or
added (which `mr repair` does not correct); the string cannot be
corrected: count its characters and check each against the engraving;
the string has 69 characters, `mr1` included: compare them with the card
length on your kit notes' digest line, where it has one (the `card
length` line `mr create` or `mr upgrade` printed)", the string's length
as typed, spaces and hyphens between groups left out, which a character
left out or added changes.
A string over 93 symbols or under 13 after `mr1` is refused by its length before any correction, with the tails the other verbs give (the over-93 one too says "`mr repair` cannot correct it"); a lone `mr1` (a space typed after it) keeps its own refusal, as in every reader: ``string 0 is `mr1` alone: a space after mr1 splits the string; give the string without that space, or quote it whole``; `repair` exits 2.
A single-string card given among a chunk set's strings is named ("string
i (strings count from 0, as in `mr repair`) is a single-string card, not a chunk (every chunk string begins
`mr1l`): read it on its own, and give the chunk set without it"), and
arguments after an `mr1…` one that look like the groups of one string
split by the shell at its spaces (each not starting `mr1` and at most 12
characters) are refused naming that ("quote the whole string ('mr1… …
…') or give it without spaces"); a longer one is a string whose `mr1`
was misread, refused as that string, with its index. `decode` and the
other reading verbs say the same. A chunked card given as one quoted
value (`'mr1… mr1…'`, each string in its groups or not) is read as its
strings: each piece that starts `mr1` starts a string.

## `mr member`

Print one member (e, s) of the set as split-chain descriptors, an md1
card or a BIP 388 wallet policy. It runs every hand-out guardrail
(open, clamped, reorder, lock-up and its window, deadline, horizon),
prints the slot's description, lock dates, costs and minimum deposit,
and warns when one key alone spends. With `--for-spend` it prints the
member as the source of a sweep instead: `importdescriptors` JSON on
stdout and the step-by-step Core recipe on stderr.
A `--for-spend` seed that nothing on a no-fingerprints card checks (no plate or
record at its seat) is never refused: it warns ``nothing on this card checks
these seeds: a wrong seed or passphrase gives descriptors that find nothing;
check with `mr verify MR1_CARD --network N --seeds "THESE_SEEDS" --keys "KEY_1"
"KEY_2"`, KEY_1, KEY_2 and so on a record or plate for each seat those seeds
fill, one quoted value each``, after its `seat @1: unconfirmed` line.

The reorder re-test refuses, unless given `--reorder-slot`, a row whose
paths open in another order than at slot 0 for any deposit from the tip
to the member's last hand-out tip, at the tip or later (owner ruling
"Refuse at hand-out", spec §6). When the order holds now and inverts for
a later deposit, the refusal reads ``the order of paths inverts for a
deposit after <date>: give `--reorder-slot` to hand it out``, and with
the flag ``deposit before <date> or the order inverts`` is printed; a
row that inverts only for later deposits (spec §10's positive heir
shift, the `3of5-2heirs` preset's `classic` rows) therefore takes the
flag at every hand-out. With `--reorder-slot`, an inversion that already
holds for a deposit at the tip prints first ``the order of paths is
already inverted for a deposit now: the <keys> path opens before the
<keys> path``. `create` checks the order only up to two horizons past
its tip (`--check-all-epochs`, below), so a later epoch meets this test
first at hand-out: read its inversions and give `--reorder-slot` to
consent, as `create` would have asked, or move the funds by "Moving to
a new set" (spec §7a step (2)), never to slot 0, as for every other
refusal there. An own-wallet row only warns, as
before. `address` runs the same test.

Every run of `member` that prints a member prints on stderr, after its
output, the Coldcard line of `create`'s closing
checklist ("a Coldcard signs as the
first registered wallet with the same keys unless you start from the
member's own wallet (Settings > Multisig/Miniscript > \<wallet\> > Sign
PSBT, …) or a host sends that wallet's name over USB; … one member per
PSBT"), since a co-signer or heir who registers or signs a member never
sees that checklist. A refused run, and a usage error (exit 2), print
none. A run given seeds, in every form and with `--for-spend`, ends its
stderr with ``this output carries your seeds' keys: never keep it beside
your seeds, since with them it tests the passphrase``.

`--as descriptor` prints its descriptors in `h` form, with the checksum
`export` prints for the same member. Each xpub in them is the card's
form (depth and parent fingerprint of no device's key), so it will not
match a device's or an mk1 plate's xpub text; plain `--as descriptor`
says so and names each seat's check to compare instead ("compare seat
checks: @0 sc:…, …"). `--as policy` heads the policy "policy (for
registration on a signer holding seat @0):", or "… holding one of seats
@0, @1):"; when your seeds fill some of those seats and plates fill the
others, it adds which are yours: "… holding one of seats @0, @1; your
seed: @1):"; a seed that agrees with the plate at a seat counts as yours there.

A height the tip has reached prints as "(reached)" and an open row's lock
(the row's, not any height of 1 or below) as "(any time, an open row)", never as a date (a date
extrapolated backward from the tip moves with the tip, and one for height 1
would predate the chain); a height still ahead keeps "(≈ date)". `member`
prints each deadline once. A slot or epoch out of range is refused with the
valid range: "slot 5 does not exist: the card has 2 slots; slots are 0 … 1"
(one slot: "its only slot is 0"), "epoch 20000 does not exist on this card:
the last valid epoch is 9,488 (spec §5)".

With `--for-spend` the stderr notes also list each path of the member
by what you gave: "path @1: your seeds sign it; opens 2034-08-28 (4.4
years)" (a wait under a year is in days: "opens 2026-10-01 (6 days)"), "path @0: nothing you gave signs it: it needs @0; open now"
(a relative lock after an absolute one adds ", then N days after each UTXO
confirms"; a path with a relative lock alone reads "opens N days after each
UTXO confirms"). A path
of a quorum names it as the role table does ("path 3 of @0, @1, @2, @3,
@4: your seeds sign it; open now"). A
co-signer is told its share and every way to finish: "path @0, @1, @2:
your seeds give 1 of the 2 signatures it needs; the rest: @0 or @2", or
"… the rest: any 2 of @0, @1, @3, @4". The spend recipe is commands, for bash, zsh, dash and fish alike, with
the capitals for you to fill in (a note first says that `bitcoin-cli`
carries the run's chain option, `-testnet`, `-signet` or `-regtest`, as
`export` prints it). Step (1) is `bitcoin-cli … -named createwallet
wallet_name=WALLET_NAME disable_private_keys=true blank=true
descriptors=true`, the `mr member … --for-spend --as descriptor … >
import.json` run that saves the JSON (the card's strings in canonical
form, separators dropped and lower case, however you typed them, so a
grouped string you typed in quotes does not split when pasted; the
network, epoch, slot and tip, then the keys you gave, double-quoted as you gave them,
`--keys-file KEYS_FILE` for a file, and `--seeds "GIVEN_SEED_1"` (`"GIVEN_SEED_1,GIVEN_SEED_2"` for
two; `GIVEN_SEED_01` … from ten seeds, as `export`'s spend lines name them) for the seeds, then each `--seat-check SET_ID:@i=sc:…` value the run was given, as `export`'s spend line keeps them, so a seat this run ties is tied at every step that re-runs it), and `tr -d '\n' < import.json | bitcoin-cli … -rpcwallet=WALLET_NAME
-stdin importdescriptors` (`-stdin` takes one argument per line, so `tr`
puts the JSON on one line; several members go in one call: each run prints
one member's two descriptors as a JSON array, so join their entries into
one array, one `[` and one `]` around all of them, before the call); under `--as policy` stdout is a policy, and
the step says the JSON is the descriptor form's. The rerun lines carry the
run's `--open-slot`, `--accept-stub-mismatch`, `--accept-unconfirmed-seeds`,
`--seed-language` and `--accept-seed-language` when it was given them. Step (2) is `listunspent`: note the `txid` and `vout`
of the member to be swept, since the wallet holds every member imported in
step (1). Step (3) leads with `sendall`, the simpler no-change sweep: it
gives each path's lock fields and, under them, its `sendall` command:
`-named sendall recipients='["DESTINATION"]'
options='{…}'` (when the run gave signers, the paths its signers sign come first,
and, when the paths differ in that, each path line ends with the verdict: ``(your
seeds sign it)``, ``(your seeds give 1 of the 2 signatures it needs; the rest: @0 or @2; build its PSBT here and have the other signers sign it in step (4))`` for a co-signer's path, or ``(nothing you gave signs it: …; skip it, or add the keys it
needs)``, so the first `sendall` is never a path the run cannot sign), DESTINATION being, by who runs it: the address `mr
address` gave (the owner's or a co-signer's run, which migrates to the
current epoch); for seeds with the heir's shape (below), "an address of a
wallet of your own, never this card's: as an heir spending after the
owner, sweep with no change out of the card, not to the current epoch,
whose paths open to the other keys before yours (§7a)"; for a run given
no seed, or at a tip with no receivable epoch, both ("the address `mr
address` gave, or, if you are an heir spending after the owner, an
address of a wallet of your own, never this card's (§7a)"); and under
`--compromised`, "a place the destination rule below names, never an
address of this card"; always with `"inputs"` (`TXID` and `VOUT` for you to fill in,
one object per UTXO of the member; a relative lock adds each object's
`"sequence"`), because `sendall` without `inputs` sweeps every UTXO of the
wallet, other members' too; `"locktime"` for an absolute lock,
`"psbt":true` (the wallet only watches) and `"fee_rate":FEE_RATE`
(FEE_RATE, the fee rate in sat/vB, for you to fill in: a node with no
fee estimates, such as one just synced, refuses `sendall` without
one). The command line is the command alone; the explanation is in step
(3)'s prose, which then names `walletcreatefundedpsbt` as the manual
alternative: every UTXO of the member an input (`"add_inputs": false`)
and one output with `"subtractFeeFromOutputs": [0]`, so there is no
change, with a `"fee_rate"` in sat/vB, passing the chosen path's lock
fields explicitly (Core defaults `locktime` to 0, which fails every
`after()` path). Step (4) is the command `mr member CARD
--network N --epoch E --slot S --for-spend --as policy --height H --time T
--seeds "GIVEN_SEED_1"`, CARD being the card's canonical strings as in step
(1), in either form (a plain `mr member --as policy` refuses an heir
past the deadline); a run given seeds adds that a seed held as an ms1 plate is
restored on the signer from its words (`ms decode "MS1_PLATE"`, the plate in one pair of quotes, turns the plate into them)
before the policy is registered and signed. Your
seeds sign; an mk1 plate beside them signs nothing (a kit's plates are
the seats whose seeds it lacks); a run given plates alone counts them
as its signers' devices. "key @i alone spends" names only such a
signer; on a `tr` card it adds that @i is the card's seat, not the policy's key
number (``key @0 alone spends now (seat @0 of the card; the policy's key numbers
differ: `mr member --as policy` prints the map of policy keys)``; in a `--for-spend` run, where that run refuses the deadline at a spend-time tip, ``… this run with `--as policy` prints the map of policy keys)``). The migrate-on-spend advice is printed on every run. When the
seeds you give are in no signing set of a path of slot 0 that is open
today, only of a later one (an heir's shape; a co-signer of a k-of-n is
in the open k-of-n's), one more line follows it: "if you are an heir
spending after the owner (…): sweep every UTXO with no change to a
wallet of your own, as step (3) above builds it, not to the current
epoch (§7a)". A run given no seed never gets that line. A run given
the hot child's own words (not its parent's seed, which counts the child, its own words given or not)
is tested twice, with the hot child counted and set aside: the counted
test decides, except that when only the set-aside test finds the heir's
shape the run cannot be told, so step (3) names both destinations and the
line reads "if you are an heir spending after the owner (the seeds given,
the hot child set aside, sign no path of slot 0 that is open today, only a
later one): …". Whether the
seeds have that shape is read at the first epoch receivable for a lead
of at least 2,017 blocks, one past the short-delay threshold of 2,016
(or one second past 2,016 × 660 s of time), whatever
`--min-lead` is, so the line does not come and go with the lead. The
same reading picks step (3)'s DESTINATION, so the heir's step (3) never
names `mr address`'s address, the current epoch's member, which the
owner's keys spend before the heir's path opens.

## `mr address`

Derive one address of a member, to check a receive or presigned-move
destination before using it. Every run that prints an address prints,
after it, "before the first deposit to this set, check this address on
a signer's screen" (a refused run prints none). It
prints every hand-out refusal, the open one first (the reorder refusal
for a later deposit and its `--reorder-slot` lines as `member` prints
them, above); at a row other than
0 the open refusal names the slot-0 paths the row locks and the rows
that qualify instead, up to slot 0's last valid epoch (past it slot 0
has no member, and the refusal names neither): "if you are migrating: this row locked or
switched off the path of \<keys\>; … take that row's epoch from `mr
current …`", then "rows that qualify: 2, 3" and, one line per row, its
own `mr current` command to run as printed once you fill in the lead
(the card's strings in canonical form, separators dropped and lower
case, however you typed them; `--network` on every network, `--network
main` included, since a mainnet run must name it; the `--height` and
`--time` you gave, `--lead L` and `--slot` set to that row; then your
`--min-lead` when it is not the default 30 days, and `--accept-tip` when
you gave it, so `mr current` answers at the same minimum lead and tip
check: ``row 2: `mr current mr1… --network testnet --height 1000000
--time 1900000000 --lead L --slot 2` ``). A hand-out refused for its deadline (`address`,
or `member` without `--for-spend`) says, as the last line before its "why:" line, ``to
spend from this member rather than hand it out, run `mr member` with `--for-spend`, which
skips this guardrail`` (the open test still applies there). A lock that `open` set (an
`after()` opened to height 1) is lifted by `--open-slot` too: when the deadline refusal is
of such locks only, and neither `--open-slot` nor `--accept-deadline` is given, it adds,
just before that line, "(the open row's lock: `--open-slot` lifts this too)" when the open
test refused the member, whose refusal, printed first, already ends `override:
--open-slot`, and "(a lock that `open` set: `--open-slot` lifts this)" when the open test
passed it (slot 0's own deadline at that epoch already past, say), when it ends `override:
--open-slot` itself; it never names `--accept-deadline` (which still passes it), nor sends
you to `mr current`, which answers the same refused epoch:

```text
mr: deadline: height 1 (any time, an open row): already past
(a lock that `open` set: `--open-slot` lifts this)
to spend from this member rather than hand it out, run `mr member` with `--for-spend`, which skips this guardrail
why: a deadline already past or this close protects nothing
override: --open-slot
```

A refusal with any other lock past or near is the usual one. A hand-out refused for its deadline (`address`, or `member` without
`--for-spend`) says how to find the epoch to hand out: ``to hand out a member of this
slot, take its epoch from `mr current mr1… --network testnet --height H --time T --lead L
--slot S` `` (with `--min-lead` and `--accept-tip` when given). When no epoch of the slot can be handed out any more (`mr current` refuses it as ended), the line is ``no epoch of slot 0 can be handed out: <current's text>`` instead (``this slot ends at <date>; move to a new set on new origin paths, §4``, the scan refusal ``within the heir's scan this slot gives no lead of `--min-lead` …`` of `mr current` below, or the ended-2038 text), since `mr current` would refuse the same slot; there the scan refusal spells both leads in whole days, as `address` and `member` take `--min-lead` (``4000d (the longest is 3924d)``). `--compromised` refuses at every row. An index
of 1000 or more warns: the heir's scan may not reach it.

**Presigned moves** stay broadcastable until their inputs are spent and
do not protect coins past the epoch deadline: migrate to a fresh epoch
before leaving, and on return treat the transaction as live until its
coins are moved. Their fee is fixed at signing, so they need a fee
ladder or a P2A anchor. (`mr address --help` prints this advisory.)

## `mr current`

Find the nearest epoch whose every absolute lock, in slot S (default
0), is at least a lead L away, each kind in its own units (a block
counts 9 minutes). Locks set by `open` are ignored; a slot with no
other absolute lock is measured by the card's deadline functions, and
the answer then changes only the branch. Without `--slot`, each
own-wallet row is answered too (`wallet at slot s: epoch E`).

It prints the answered member's nearest absolute lock with its date and
the lead it gives (``slot 0 at epoch 3: deadline height 1,417,680
(≈ 2031-05-02); lead achieved 2,770 days``; none on an epoch-less card,
which keeps its fixed text). It also prints, for each path of the
answered member with a relative lock, `path <keys> opens about N days after each deposit confirms`,
warning when that wait is shorter than your lead, and the migration
rule: every row's funds move to the same slot of the new epoch, and
only an open row's go to slot 0.

A row none of whose locks moves with the epoch prints the template's
figure, not its own: ``slot 15 at epoch 0: the template's deadline D(e) is
height 1,260,000, since no lock of this row moves with the epoch``; a row
with a moving lock keeps ``deadline height``. An open row at the tip prints
``slot S is an open row at epoch E: its funds migrate to slot 0 (§7a)`` and
then the lines `address` prints for it (``if you are migrating: … keep these
funds off slot 0``, ``rows that qualify: N`` and each row's `mr current …`
command), none when the open row locks no path that is open at slot 0.
Past slot 0's last valid epoch, where slot 0 has no member, an open row
prints ``slot S is an open row at epoch E, and slot 0 has no member here:
move this row's funds to a new set (§7a 'Moving to a new set')`` and no
such lines.
When the tip's time disagrees with the release's anchor by more than a
tenth of the anchor's age at the tip, the refusal says ``this release's
anchor is N days old at this tip, which does not explain a gap of G days:
check `--height` and `--time` (`blocks` and `mediantime` in your node's
`bitcoin-cli getblockchaininfo`)``; a smaller gap keeps ``if the tip is
right, use a current release``. A refused tip check reads the disagreement
first, then that remedy, and the tip echo (``tip = H, ≈ DATE; this must be
the current tip``) last. A date past the year 9999 reads ``after the
year 9999``, and an open row's lock at height 1 prints ``(any time, an open
row)``.

It never offers a lead below `--min-lead`: a `--lead` below it is
searched at `--min-lead`, with the warning ``--lead L is below
--min-lead M: the lead used is M, since `current` never offers a lead
below --min-lead (§7)``, so the epoch it answers is one whose
deadlines `address` accepts at the same `--min-lead`, in whole days
(`address` also runs its open, lock-up and horizon checks). The
warning for a path that opens before your lead compares with the lead
used. A lead typed as a bare number is printed with its unit (`--lead 400` reads
"before your lead of 400 days").

It refuses when no epoch meets the lead: `no epoch of slot S meets
lead L; a lead of at most <L′> still reaches epoch <E>` while one
still meets `--min-lead`, else `this slot ends at <date>; move to a new
set on new origin paths`. Past the heir's default scan it answers the
last epoch of the scan and prints the lead achieved (`lead 9.4 years:
the most the heir's default scan covers`), or refuses ``within the
heir's scan this slot gives no lead of `--min-lead` 11.0y (the
longest is 10.7y): move to a new set, or give the `--min-lead` you
meant`` when that lead is below `--min-lead`: the minimum in force and
the scan's longest lead in one unit, spelled as `--min-lead` takes it, so
the years, days and hours forms can be given back (the "none" and
"less than …" forms below cannot), tenths of years (`11.0y`) from a year up,
whole days (`25d`) from a day up, else whole hours (`5h`), the minimum
rounded up and the lead down, the lead "none" at or before the tip and "less than 0.1
years", "less than 1 day" or "less than 1 hour" when it rounds to 0;
with no `--min-lead` given the minimum reads ``30d (the default)``
and the text ends at "move to a new set". On a slot still valid past the scan, a lead no epoch of
the slot meets at all (`--lead 9999y`) is answered the same way, at the
scan's last epoch with that lead line; under `--beyond-horizon`, or on a
slot that ends within the scan, the `no epoch of slot S meets lead L`
refusal stands (a slot whose last epoch is the scan's last, or earlier).
An epoch-less card answers epoch 0 for any lead. At a
tip past 2038-01-19 a slot whose member carries a time lock has no
epoch, and `current` answers only the other slots, saying for the
others to move the funds to a new set on new origin paths. It takes no
`--compromised` and prints no reminder.

### Synopsis

```sh
mr current [OPTIONS] --height <H> --time <T> --lead <L> <mr1>...
```

### Flags

| Flag | Purpose |
|---|---|
| `<mr1>...` | The card's strings (one, or each chunk of a chunked card) |
| `--height <H>` | The tip's block height (`blocks` in your node's `bitcoin-cli getblockchaininfo`) |
| `--network <NETWORK>` | Network: main (default; `mainnet` is accepted too), signet, testnet or regtest [default: main] |
| `--time <T>` | The tip's median time past, unix seconds (any u32) (`mediantime` in your node's `bitcoin-cli getblockchaininfo`) |
| `--accept-tip` | Accept a tip whose height and time disagree with this release's anchor by more than 180 days |
| `--lead <L>` | The lead: how far every absolute lock must be from the tip (2y, 26w, 30d, 36h; a bare number is days; a block counts 9 minutes) |
| `--slot <S>` | The slot S (default 0; without it, each own-wallet row is answered too) |
| `--min-lead <L>` | The minimum lead: never offers a lead below it (default 30 days) [default: 30] |
| `--beyond-horizon` | Answer an epoch beyond the heir's default scan |

### Worked example

```sh
mr current mr1… --network testnet --height 1000000 --time 1900000000 --lead 5y
# tip = 1,000,000, ≈ 2030-03-17; this must be the current tip
# slot 0: epoch 1
# funds at slot 0 migrate to slot 0 of epoch 1; every row keeps its slot, …
```

## `mr units`

List the units of a template or card in order, each with its keys and
locks and whether `off`, add-wait and add-deadline are available there,
marking a unit whose `off` would be refused, and marking ``internal error
(a bug): its written form fails its type or sanity check; please report
it`` on an operation whose written form would fail as a row's only
operation (a bug in `mr`; the other units are listed as usual). A unit whose operation
the member row check refuses for the script's size is marked with the size, told apart by
the script it would make: ``refused by the member row check (its P2WSH script would be over
3,600 bytes, which is not standard)`` for a P2WSH script, and ``refused by the member row
check (its P2SH script would be over 520 bytes, the most a spend may push)`` for a bare
`sh()` template's script. On a bare `sh()` template every add-wait and add-deadline (and
any operation leaving a body other than a plain `pk`, `pkh`, `multi` or `sortedmulti`) is
marked ``refused by the member row check (its bare `sh()` body would not be a plain `pk`,
`pkh`, `multi` or `sortedmulti`, so Bitcoin Core could not scan it)``, which comes before the
size mark. `decode` prints the same marks under its unit lines. Unit texts are written as
rust-miniscript prints them (`sln:older(144)`, never
`s:or_i(0,n:older(144))`). On a template typed out of first-appearance order, `units` prints the map once (``stored numbering: typed @1 = stored @0, typed @2 = stored @1, …``) and labels each unit and each key in both numberings, stored and typed: ``unit 1 (branch): `and_v(v:pkh(@3),older(52560))` (typed `and_v(v:pkh(@4),older(52560))`); keys @3 (typed @4); locks older(52560)``; a template typed in order prints one numbering, as before, so a typed `@j` is never read as a stored one. `units` also reads an md1
card (every other verb refuses one at a card argument): it lists the
md1's units in its stored numbering, the order `upgrade --slots` takes.
`--template-preset <name>` stands for the preset's template (as in
`create`), so a creator writing `--slots` for a preset does not retype
the template; an unknown preset is refused naming the presets, and a
template beside it is a usage error.

### Synopsis

```sh
mr units [OPTIONS] <template|mr1>...
mr units [OPTIONS] --template-preset <name>
```

### Flags

| Flag | Purpose |
|---|---|
| `<template\|mr1>...` | A template (one argument), a card (one `mr1` string or its chunk set), or an md1 card (its units in the order `upgrade --slots` takes) |
| `--template-preset <name>` | A template preset instead of a template (as in `create`): owner-heir, 2of3-heir, 3of5-2heirs, or any of them with `-tr` |
| `--network <NETWORK>` | Network: main (default; `mainnet` is accepted too), signet, testnet or regtest [default: main] |

## `mr create`

Issue a new mr1 card from a template or preset: its keys, a slot table
and a tip. `create` runs every guardrail before it mints anything, and mints
on mainnet when `--network` is main or not given. It never
generates a seed: every seat's key comes from `--keys` (in the numbering
the template was typed in), except the hot seat's, which it derives from
the hot child.

A lock-up row whose owner path opens less than `--min-lead` before
another path is refused (`--lockup-no-window`) with one line per pair
of paths, its epochs merged into ranges and its windows into their
least and greatest: `slot 1, epochs 0-19: the @0 path opens 1,000
blocks before the @1 path, less than --min-lead` (`upgrade` the same).

A template constant that no rust-miniscript form covers (a `0` or `1`
other than those of `t:`, `l:`, `u:` or `and_n`, as in `andor(X,0,Z)`)
prints bare, and Coldcard's parser refuses it. `create` and `upgrade`
still mint the card, and warn on stderr once for each such constant, in
the order the template writes them, naming the branch that holds it (or
the whole-script root unit of a template with no branch) by the number
`mr units` gives it: ``warning: template has a bare 0 or 1 at unit <n>:
Coldcard's parser refuses it``; two constants in one branch give two
lines. A constant outside every branch of a template with branches is
``warning: template has a bare 0 or 1 outside every branch: Coldcard's
parser refuses it``, whether or not the template has a root unit. They
print no warning for `t:`, `l:`, `u:` or `and_n`, nor for a template
with no miniscript (`wpkh(@0)`).

**How far `create` checks** (owner ruling "Two horizons", spec §6). The
reorder and lock-up window tests, the two that sweep epochs, run from
the first receivable epoch e_f to each row's last checked epoch
min(E_s, max(e_f, e₂)), e₂ being the heir's default-scan epoch (§7's
e_hi, as `export` computes it) at the run's tip with twice the card's
horizon: 20 years by default. When that stops some row before its last
valid epoch, `create` and `upgrade` print ``the reorder and lock-up
window tests checked each row to epoch <c> (slot 0's earliest deadline
there about <date>); a later epoch is checked when `member` or `address`
hands it out; `--check-all-epochs` checks every epoch to each row's
last``, the date at 9 minutes a block from the tip.
`--check-all-epochs` runs both sweeps to every row's last valid epoch;
when the cap stops no row (a card with no epoch axis, or whose only kind
is time), it warns `` `--check-all-epochs` changes nothing here ``. The
open test of an own-wallet row, the consent-bit warning, the one-epoch
tests and the refusal of a row of more than 100,000 epochs keep their
whole range. A row may outlive slot 0 (a removal or an earlier shift of
slot 0's latest lock): past slot 0's last valid epoch these tests, and
`member`'s and `address`'s hand-out lines, compare the row with slot 0's
paths as the template writes them there, each lock at its value, in its
kind's range or not, so every epoch is decided and slot 0's own invalid
member is never the verdict (member (e, 0) itself stays invalid and is
never handed out). That refusal names the bound and a delta that fits: ``slot 1: the guardrails
would test 123,456 epochs, more than this release walks for one row (at most 100,000); use a
delta at least 1.24 times the one given (slot 0 is not range-walked)``.

(`--keys`, needed with `--seeds` too: a seed checks its seat's letter
and supplies no key; each key is the xpub its seat's signer exports at
the seat's path, `m/270028'/1'/(32·r + i)'` on a test network, where i
is the seat's **stored** number: when the template is typed out of
first-appearance order that is not the typed `@j` (`mr units` labels
each unit and key in both numberings, stored and typed; typed @1 = stored @0 for a template that begins `multi(2,@1,…`),
and the refusal names the path for every seat), a
slot table (`--slots` or `--preset`), a `--role` per participant, and the
sibling question: every existing card of yours on these origin paths as
`--sibling` (each followed by its `--sibling-keys` when needed), or
`--no-other-cards-on-these-paths`. `--sibling-keys` binds to the
`--sibling` or `--bundle-card` before it. Each of its keys goes only to
a seat of that card, at the key's origin path, that it is identified
with:

- `@i=<key>` binds seat i;
- an unbound key goes to the seat at its origin path whose Pubkeys TLV
  key it is; else to the one open seat there whose declared master
  fingerprint it carries; else, once those are placed, to the one open
  seat left there that it may be. An open seat has no key yet and no
  Pubkeys TLV key; a key may be an open seat's when that seat declares
  its fingerprint or none, or the key carries none (a declared or
  carried `00000000` counts as none);
- unbound keys that may each be several open seats' keys at their path
  fill, in any order, every open seat there that one of them may be,
  each key a seat of its own (the seats are then keyed, but none is
  identified; an open seat that none of them may be, since it declares
  another fingerprint, stays unknown). Fewer keys than those seats are
  refused as undecidable: give every key of that path, or bind each
  with `@i=`. Keys that cannot each take a seat of their own among those
  seats are refused: one of them is not that card's key;
- refused (exit 1): a key whose origin path is not its bound seat's, or
  no seat's; a seat the card lacks; a key whose master fingerprint is
  not the one the card declares for its seat, or none it declares for an
  open seat at its path (a key that carries no fingerprint, or
  `00000000`, is never refused for it, since it decides nothing); a key
  that contradicts the card's own Pubkeys TLV key for its seat; more
  keys at a path than the card has seats there; a key given twice for
  one card (on a card whose Pubkeys TLV keys the seat too: ``plate 1 and plate 2 carry the same key: the same key is given twice; drop one``).

So on a card whose seats share a path (a BIP 48 multisig's
`m/48'/1'/0'/2'` for every seat), give every key of that path, in any
order, or bind each with `@i=`, unless the keys carry the fingerprints
the card declares. The collision test compares every key known for a
given card against every seat of the new card, whichever seat it went
to. It then tests every seat of the given card at a new seat's path by
master fingerprint, its key known or not, when both cards declare one
for it other than `00000000` (which counts as none, and two `00000000`
are not the same fingerprint): the same fingerprint collides, different
ones do not. A seat whose key is unknown and that no two fingerprints
decide is tested by its seed letter when both cards have seat maps (an
`mr1` card), else refused as undecidable. A collision names the seat the
key is identified with, or, for keys that filled a path's
undistinguished seats, those seats ("seat @0 or @1"). A seat's

**The ms1 restore note.** `create` and `upgrade` print, once, in the
notes of every kit that holds an ms1 plate (a seed's, or the hot
child's own), and in no other kit, how to put a seed on a signer and
how to read an ms1 plate by hand, word for word:

> to put a seed on a signer, enter its words, never its ms1 string: decode the plate to its words offline (`ms decode "MS1_PLATE"`, the plate in one pair of quotes, or by hand, below) and use the signer's import by words (a Coldcard takes 12, 18 or 24 English words; a 15- or 21-word seed, or one in another list, needs another signer). Never use a Coldcard's Import Codex32, or any codex32 import, on an ms1 plate: it reads an ms string as a raw master secret, not as words; Coldcard refuses these plates' lengths, and a string it took would restore another wallet. By hand: ignore spaces and hyphens, read upper and lower case alike, drop the first 9 characters (`ms10entrs`) and the last 13 (the checksum); read each other character as 5 bits by its place in `qpzry9x8gf2tvdw0s3jn54khce6mua7l` (q = 0, l = 31); join them, read bytes of 8 bits and drop the 0 to 4 bits left over (all 0s). A first byte of 00: the rest is the seed's entropy, read in the BIP-39 English list unless this kit's notes give a language for this plate's letter (then decode with `ms decode --language LANGUAGE`, LANGUAGE the language those notes give). A first byte of 02: the second byte names the list (0 English, 1 Japanese, 2 Korean, 3 Spanish, 4 Chinese simplified, 5 Chinese traditional, 6 French, 7 Italian, 8 Czech, 9 Portuguese) and the entropy starts at the third byte. Never write the words in another list. The entropy is 16, 20, 24, 28 or 32 bytes for 12, 15, 18, 21 or 24 words; read its bits 11 at a time, each a word's place in the list, counting from 0. The last word is short: its remaining 7, 6, 5, 4 or 3 bits are the start of its place, and the rest of its place is a checksum that needs a computer (the first 4 to 8 bits of the entropy's SHA-256); without one, use the signer's last-word tool where it has one: from a Coldcard's list of valid last words take the one word whose place starts with those bits, or, for 12 or 24 words, give a SeedSigner's Calc final word those bits. Checking the plate's own checksum also needs a computer. Where a plate carries a Standard SeedQR, a signer that scans one (SeedSigner, Coldcard Q) reads each English word as its place in the list, counting from 0, written as 4 digits ('12' as 0012).

sharing form, `create` only; `upgrade` refuses it as a usage error)

no hot seat and writes the named card's child entry, from seed L or from
a record. A named card with no hot seat is admitted by its entry
(``set <id> has no hot seat: its child <len>/<i> is taken as this one by
its entry alone, unconfirmed (a child letter matches 1 time in 16 by
chance); the closing sitting checks it with seed <L>``), once the
own-card question is answered yes; a no is refused, ``set <id> is not
counted as your own card: the sharing form names only a card that is
seed <L>'s history: answer yes only if it is, or drop `--hot-on <id>` ``.
A new card with no hot seat given a history card prints the hint ``to
name set <id>'s cheap hot wallet on this card in place of a new child,
pass `--hot-on <id>` (the sharing form)``.

### Table and card checks

A table of 100 operations or more prints at once on stderr ``checking the
slot table: R rows of U operations (N in all); a large table can take a
while`` (a 16-unit table on a height axis with 31 rows takes, as the journeys
measured it at 4 CPUs, about 21 s with `--reorder-slot` and
`--check-all-epochs`, which test each row at every epoch, and about 10 s
when the table is refused; the same table with the default horizon cap, two
horizons past the tip, takes 4 to 5 s). A row whose
member at epoch 0 is invalid names the lock, its value and the bound it
breaks, and the `--slots` line: ``` `--slots` line 3 (slot 1) has no valid
epoch: its member at epoch 0 is invalid: its `after(2,175,251,200)` is a
time above 2,147,483,647 (2³¹ − 1), the largest `after()` time (spec §5)```
(a height at 500,000,000 or above would read as a time; below 1 is
refused); every refusal that begins "slot S" names its file line the same
way. More than 31 rows is refused ``a card declares 1 to 32 slots, slot 0
and at most 31 `--slots` rows; this table has slot 0 and N rows, N+1
slots``. The open print groups the epochs by their keys and reason, each
line with its own reason and date. A card without an epoch axis prints no
earliest-epoch, receiving-epoch or migrate-on-spend line (``epoch 0 only
(this card has no epoch axis)``), and a count of one is singular (``1
epoch``, ``seat @0``). Keys bound to the wrong seats are named by the
seat they belong to (``it is the path of typed @1: bind it `@1=` only if
that key's holder belongs at typed @1 (`mr units` labels each key in both

## `mr upgrade`

Issue an mr1 card whose member (0, 0) is the wallet of an existing md1
card, so the wallet you already funded becomes the card's first member.
`upgrade` is `create` over the md1 card's descriptor, in the md1's own
numbering (`@i` is the md1's `@i`): the template, the origin paths and
the path convention's rounds are the md1's, and every other rule,
guardrail and print is `create`'s (the `--preset classic` repeat
warning among them). It mints on mainnet when `--network`
is main or not given, and never generates a seed. An md1 whose paths
are the path convention written out (`m/270028'/<coin>'/<32r + i>'`)
becomes a path-convention card (the flag, the purpose number and the
rounds replace its paths, and `upgrade` says P differs); an md1 at any
other purpose (BIP 84's `m/84'/0'/0'`, or a pre-release card's `499'`)
keeps its explicit paths. At `upgrade`, as at `create`, the deadline guardrail's test at the
first receivable epoch leaves out every lock that `open` set, on every row: the open test
speaks for such a lock, and each hand-out (`address`, `member`) runs the open test and the
deadline guardrail again. So an `open` row whose lock is already past (every `--preset
classic` run, whose slot 15 is `open`) passes without `--open-slot`, and an `--open-slot`
given for such a lock alone is warned as unneeded, ``warning: `--open-slot`: no row of this
card needs it at `upgrade`; the flag changes nothing``. A row marked `--own-wallet` that the
open test finds open is still refused without `--open-slot`, which then sets its
open-consent bit.

for such an index, and adds that the heir needs `--history` or `--next`

quoted. A fully keyed md1 needs none: `upgrade` derives its own

height deadline at the tip counts as past, since the heir path spends
in the next block (the (0, 0) block reads ``deadline: height 320,000 (reached): past (spends in the next block)``, not "closer than --min-lead"); a time deadline counts as past only before the tip's
time. The card is issued all the same. As `create` does, `upgrade` prints the card length line before the set id (for an owner-heir md1, for example, ``card length: 78 characters, `mr1` included, in 1 string``), and every kit's digest line ends with the same words. An heir whose kit spends (0, 0)
today, when the first receivable epoch is later, is warned, not
refused.

**Hot child.** The hot flags work as in `create`. The hot seat's key
must be the md1's: when the md1 keys the hot seat, or declares its
master fingerprint, the child the search takes must match, or `upgrade`
refuses (`` `@i`, the hot seat: … `upgrade` keeps the md1's keys ``;
check `--hot-child`, the history inputs and the parent's passphrase).
An heir listing `hot` is rerun at epoch 0 as well as at the first
receivable epoch, and needs `--heir-holds-hot-path` wherever the hot
seat makes their kit spend today. `--hot-child L` is refused when two
seats of letter L carry different fingerprints, or a role lists `L#…`.
`--hot-on` beside a given card of a newer child of the parent, or of
the other length at the same index, is refused as in `create`, but the
refusal ends "`upgrade` keeps the md1's hot child, so this md1 cannot
be upgraded on that device: move its funds with `create`, whose search
takes a new child" in place of "let the search take a new child".

`upgrade` admits two seeds that share a letter (seated by the Fingerprints
TLV, so `--no-fingerprints` is refused for them); a role then names each
as `LETTER#FINGERPRINT`. The md1 given back, as `--sibling` or
`--bundle-card`, is set aside with a note and is neither listed nor
counted in the bundle list (or refused, as below). The note says it is the card being upgraded
when every seat's key is known (from its keys or `--sibling-keys`) and
equal to the seat's, with no fingerprint that differs: the keyed md1
itself, or a keyed copy of it (the same template and origin paths). A
key identified with a seat (bound with `@i=`, the card's own Pubkeys
TLV key, or placed by the fingerprint the card declares for that seat)
must be that seat's key: a mirror wallet, whose card keys the heir's
key at @0 and the hot child at @1 where the md1 has them the other way
round, is another wallet and is refused as one key on two cards. Only
keys given unbound at a path several seats share, whose seat nothing
tells, are compared as a set, in any order, and only on a card with
the md1's own payload: a card of another payload (no Fingerprints TLV
where the md1 has one, say) with such keys is tested as a sibling;
bind its keys with `@i=` to have them compared seat by seat. Even on
the md1's own payload, such keys are trusted only where the
fingerprints the card declares tell those seats apart (each seat
declares one, all different). An md1 without fingerprints, given back
with its keys unbound at a path two or more seats share, is byte for
byte another wallet's card with those keys in other seats (a mirror
wallet whose cold seat holds the hot child, or two cold seats
swapped), so it is refused, with no override: "`--sibling` md1
1a2b3c4d has the payload of the md1 being upgraded, but its
`--sibling-keys` fill its seats @0 and @1 at m/48'/1'/0'/2' unbound, so
nothing tells it from another wallet with those keys in other seats:
bind each with `@i=`, or leave the card out". An md1 that declares no fingerprints where the md1 being upgraded does, with the md1's own keys given unbound at a shared path, is refused the same way: "`--sibling` md1 1a2b3c4d has the md1 being upgraded's template and origin paths and declares no fingerprints, and its `--sibling-keys` fill its seats @0 and @1 at m/48'/1'/0'/2' unbound, so nothing tells it from another wallet with those keys in other seats: bind each with `@i=`, or leave the card out" (a foreign key among them is a collision). Bound with `@i=` to its
own seats, it is set aside; left out, the run is the same. An
md1 with the md1's own payload and a seat whose key is unknown is set
aside too, when no key you give for it with `--sibling-keys` differs
from the seat's (at a shared path, when each is one of that path's
seats' keys, placed as above; a partial set of unbound keys that
nothing places is refused, as for any card); its note says only that it has the same
payload as the md1 being upgraded, since another keyless wallet on the same template
and paths, without fingerprints, has that payload too. Any other given
md1 is tested as a sibling, even one with the same payload: a key that
differs makes it another wallet (kept in the bundle list as a bundle
card), a shared key is refused as one key on two cards, and a seat that
cannot be decided asks for `--sibling-keys`. An md1 of the same
template, origin paths and fingerprints but with a seat whose key is
unknown (a keyless copy of a keyed md1, say) that collides is told so:
"… has the md1 being upgraded's template, origin paths and
fingerprints, but not every seat's xpub: if it is a copy of that md1, it is not its
own sibling: drop it from `--sibling`, or give its keys with
`--sibling-keys` so `upgrade` sets it aside; if it is another wallet on
these keys, the fix is `create` on a new account". An mr1 card given as
`--sibling` whose set id and digest are those of the card this run mints
is that card (an owner re-minting a lost card gives the one they still
have): it is set aside with the note "it is this card (same set id and
digest): not its own sibling (§7): set aside", and is not refused as a
collision; an mr1 card of another set id or digest on the same keys still
collides. Each kit's notes
give each seat's origin path as the card has it: the md1's own path
(such as `m/48'/1'/0'/2'`), or the path convention's when the md1's
paths are the convention written out.

## `mr export`

Export watch-only descriptors for a wallet or an heir: every member of
the chosen epochs and slots, each labelled with (e, s), its chains
("chain 2, change chain 3") and its unlock
heights or dates (a path of a quorum names it as the role table does:
"3 of @0, @1, @2, @3, @4 any time"), as ready `bitcoin-cli scantxoutset` calls in windows of
1000 indexes (main calls over indexes k·1000 … k·1000 + 999, probe calls
over the top 100), batched at 1,000,000 scripts per call (1,000
descriptors a main call, 10,000 a probe call). Each call is one line,
`printf '%s\n' '<json>' | bitcoin-cli -testnet -stdin scantxoutset start`
(the run's `--network` as Core's chain option, first: `-testnet`,
`-signet` or `-regtest`, none on `--network main`), which
bash, zsh, sh (dash) and fish all run (fish has no here-documents). The
`printf` builtin feeds the call's JSON to Bitcoin Core's `-stdin`, which
reads it as the call's last argument, so no shell argument limit splits
a call, and the single quotes keep the shell from expanding anything in
it (the JSON never holds a `'` or a `\`: `export` refuses to print one
that does). Every `bitcoin-cli` command `export` prints carries that
chain option (the scan and import calls, and the `createwallet`,
`rescanblockchain` and `getwalletinfo` texts), so a call run as printed
reaches the run's `--network`; add any connection options of your own
(`-datadir=…`, `-rpcport=…`) before `-stdin`. Stdout and the heir file
(its second line) say `network: testnet, coin type 1`, as `member
--for-spend` does. When the run prints calls (a refused run prints the
network line alone), on testnet one more line says ``network testnet:
each `bitcoin-cli` call here carries `-testnet`, testnet3's option; on a
testnet4 node write `-testnet4` in its place (Core v28 or later), unless
your bitcoin.conf selects the network (next line)`` (`mr`'s testnet keys
and addresses are testnet4's too), and on every network but main three
lines say ``bitcoin.conf: if yours selects testnet or testnet4 (a
`chain=test` or `chain=testnet4` line, or `testnet4=1`), Core refuses a
second choice: "Invalid combination of -regtest, -signet, -testnet,
-testnet4 and -chain. Can use at most one."``, ``bitcoin.conf: then drop
`-testnet` from each call here, and the file's choice applies`` and
``bitcoin.conf: if yours selects another network (another `chain=` line,
or a line such as `signet=1`), do not drop `-testnet`: that node is on
another network than this run, and a scan there would read the wrong
chain`` (on signet, "selects signet (a
`chain=signet` line)", "`testnet4=1`" and `-signet`; on regtest,
"selects regtest (a `chain=regtest` line)", "`signet=1`" and
`-regtest`): `bitcoin-cli` reads `bitcoin.conf` and picks the chain
before it runs anything, and Core takes at most one chain choice from
the command line and the file together, so a `chain=` line refuses the
printed option even for the same network (a `signet=1` line beside
`-signet` is the one agreeing pair). Dropping the option helps only when
the file selects the run's network (a testnet4 node counts for
`--network testnet`); a file that selects another network means the node
is on another chain, and the calls belong on a node of the run's
network. A descriptor
parse error, the footer says, means ``the node is on another network
than the card (testnet: run the calls as printed, against a testnet
node) or too old for the descriptor: rerunning cannot help, so check
the node's network (`getblockchaininfo`'s `chain`), then upgrade the
node``. A call line can be hundreds of kB, and an
interactive shell can cut a long pasted line short (dash keeps 4,095
bytes; bash's readline usually takes it whole), and pasting it into a
file is cut the same way, so `export` prints a note before the calls,
on stdout and in the heir file: do not paste it;
`grep '^printf ' FILE > calls.sh` copies the call lines (each starts with `printf`) from FILE, the
heir file or the output saved with `> FILE`; delete the lines you do not
want run, and run `sh calls.sh` or `fish calls.sh` (with `--history`, whose
import calls hold the `WALLET_NAME` placeholder, "replace WALLET_NAME, and run").
The heir file itself is not a script: do not run it. The output
begins with each card's bundle list as a checklist. With `--seeds` it
also derives the bundle list's accounts (the cheap hot wallet included,
with its first address and restore text) and, unless
`--no-child-discovery`, the child discovery accounts. It never refuses
over a tip: the tip check is a warning.

**From a scan hit to a spend.** Each member line names the member's
receive chain c = 2·(S·e + s) and its change chain c + 1 after its tag:
``member (1, 0) [card 01a0adbd]: chain 2, change chain 3; @0 any time;
@1 from height 1,312,560 (≈ 2035-07-23)``. After the line on reading a
call's `success` and `unspents`, stdout and the heir file say how an
output a call finds maps to its member: ``to spend what a call finds:
each output it finds (an entry of `unspents`, or of `listunspent` after
the import) has a `desc` whose keys read [FINGERPRINT/…/C/I]: the last
two steps of a key's path, /C/I, after the seat's origin path, are chain
C and index I, and chain C is the member (E, S) listed above whose line
reads "chain C" (its receive chain) or "change chain C" (its change
chain)``; only keys that carry a seat's origin count (a bundle or
discovery account also uses chains 0 and 1), and several cards or seatings
can list the same chain: try each of their spend lines in turn. So an
output whose `desc` holds `[587b44d1/270028h/1h/0h/2/5]` is index 5 of member
(1, 0)'s receive chain. Then ``then run the command on the line after each
`spend line of` header of that member's card (and seating), as one line,
with EPOCH and SLOT replaced by E and S, HEIGHT and TIME by the current tip
(`blocks` and `mediantime` in your node's `getblockchaininfo`), each
GIVEN_SEED_N by the Nth seed given to `--seeds` in this export (the header
says which seed that is), inside the quotes as printed, and a PLATE_N by the
Nth plate given to `--keys`: `mr member --for-spend` prints the spend's
recipe; a bundle or discovery account's funds are restored as its line
above says``, and two lines per card (per seating, when a card is exported
with several, tagged as that seating's members are), a header and the
command:

```text
spend line of [card 01a0adbd]: GIVEN_SEED_1 is seed 1 (letter A, fp 587b44d1); the command is the next line
mr member mr1… --network testnet --for-spend --epoch EPOCH --slot SLOT --height HEIGHT --time TIME --seeds "GIVEN_SEED_1" --keys "@0=mk1… mk1…"
```

A seat the line binds a plate to that this run was given a `--seat-check`
value for keeps the value on the line, `--seat-check 0bcbf7c8…:@0=sc:…`
(the card's set id, as the kit notes print it; not the `[card …]` digest
prefix of the header), after `--keys`: it ties the
seat on the spend run as it did on this one, and a plate swapped later is
caught. A seat given no value adds none.

The header says what each GIVEN_SEED stands for (a line that gives no
seed says so first: ``this line gives no seed: an heir who spends adds
their own with `--seeds "THEIR_OWN_SEED"` (`member` and `export` take no
passphrase: leave such a seed out: its seat's mk1 plate, on this line or
given with `--keys`, stands for it), or the recipe counts every plate as a
signer``, or, on a line that gives no plate either, every seat keyed by the
card, ``…, or the recipe says of every path that nothing you gave signs
it``, whose parenthesis ends ``leave such a seed out and give its seat's
mk1 plate with `--keys` ``), flags a seating that uses
a seed `--child` declared (`mr member` takes no `--child`: drop the seed it
refuses), and for a command over 4,095 bytes (dash cuts a pasted line there)
says to copy that one command line (not the whole file) into a script file with an
editor, fill in the capitals and only then run `sh spend.sh` or `fish spend.sh`. With ten or
more seeds the names are zero-padded (`GIVEN_SEED_01`).

The card is written as its canonical strings, the seeds the seating
seats as `GIVEN_SEED_n` (n: the seed's position in this run's `--seeds`)
in one quoted value (a seed that agrees with a seat a plate or the
card's own key fills is kept too, so the heir's own seed stays on the
line beside that plate or key), and each key that fills a seat bound to it with its
strings (`"@0=…"`; a key with a character a shell could read is written
as `@0="PLATE_1"`, quoted); `--seed-language`/`--accept-seed-language` follow the
line's seeds. The line has no `$(…)`, no here-document and no `<…>`, so
it runs in bash, zsh, dash and fish once its capitals are filled in.
`member` asks for any consent the spend needs (`--open-slot`,
`--accept-unconfirmed-seeds`) and names it. Under `--history` the lines
follow the history outputs on stdout.

### Synopsis

```sh
mr export [OPTIONS] <mr1>...
```

### Flags

| Flag | Purpose |
|---|---|
| `<mr1>...` | The card's strings (one, or each chunk of a chunked card) |
| `--card <mr1>` | Another card of the bundle, scanned with the same keys or seeds (a chunked card's strings in one value, separated by spaces); repeat for each card. With `--card`, a card that cannot be read, or that its TLV keys with no `--network` given, is named by its place (``card 2: the mr1 checksum does not verify …``), the positional card being card 1. A value may hold a string typed in groups, with spaces or hyphens: it is read as the positional card is, so it is counted without them |
| `--network <NETWORK>` | Network: main (default; `mainnet` is accepted too), signet, testnet or regtest [default: main] |
| `--keys <mk1…\|records>...` | Keys: mk1 plates (in groups or not, as `mk encode` prints them; a chunked plate's strings in one value, separated by spaces, or as values one after another) or `[fingerprint/path]xpub` records, each optionally `@i=`-bound |
| `--keys-file <file>` | A file of keys: one key per line (a plate or a record, with its `@i=` binding where it has one), a chunked plate's strings as consecutive lines |
| `--seeds <seeds>...` | Seeds, seed 1 first: each an ms1 plate or BIP-39 words; a seed's words separated by spaces, seeds separated by commas |
| `--seed-language <n>=<lang>` | The wordlist of seed n: `<n>=<lang>` (english, japanese, korean, spanish, chinese-simplified, chinese-traditional, french, italian, czech, portuguese) |
| `--accept-seed-language <n>` | Consent to use seed n in a language other than English |
| `--height <H>` | The tip's block height (with --time; `blocks` in your node's `bitcoin-cli getblockchaininfo`): the default scan, epochs 0 … e_hi |
| `--time <T>` | The tip's median time past, unix seconds (with --height; `mediantime` in your node's `bitcoin-cli getblockchaininfo`) |
| `--horizon <D>` | The horizon in years (default: the card's horizon field, else 10) |
| `--epochs <a..b>` | Scan epochs a … b (inclusive) instead of the default range |
| `--exhaustive` | Scan every valid epoch |
| `--next <k[:target]>` | Emit window k of the run (k ≥ 1, or 0 with a target; at most 2,147,482), optionally narrowed to targets, repeated with one k: `[<digest prefix>:]<e>/<s>` (the prefix 8 to 16 lower-case hex digits), or a bundle entry (`held:84:0`, `C:84:0`, `A/24/0:86:0`). SAME_ARGUMENTS, in a command `export` prints, is this run's arguments less its --next, --heir-file and --history values |
| `--history` | Check history, spent or not: the gap-20 address-index output and the Core rescan, instead of the quick scan |
| `--child <n>=<letter>/<12\|24>/<i>` | Declare given seed n to be the child `<letter>/<len>/<i>` a bundle entry names (e.g. `2=A/24/0`), as a `hot` kit's child plate reads |
| `--try-seatings [<K>]` | Export every seating of the undecided seats, up to K! of them (default K = 4, i.e. 24) |
| `--heir-file <file>` | Also write window 0's calls, headed by the set id, card digest, tip, horizon and epoch range, to this file: a pre-exported fallback whose scan calls need no `mr` and whose spend lines run `mr member` (it holds every descriptor, so every address) |
| `--no-child-discovery` | Leave out the child discovery scan (account 0 of each given seed's BIP-85 children 0 … 15, both lengths, four purposes) |
| `--seat-check <[SET_ID:]@I=sc:HEX>` | A seat's seat check as its holder compared it, as the kit notes give it: the card's set id (or its 8-hex-digit prefix) and a colon (optional on a run of one card), then `@i=sc:` and the 32 hex digits; ties a seat nothing on the card ties, and refuses a different key. Repeatable, one value per flag: write the flag before each value (`--seat-check VALUE_1 --seat-check VALUE_2`; a second value after one is refused, naming the flag) |

Every run but a `--history` one ends its calls with the advice ``run `--history` as well
for: …``. A `--next` target the card lists that no given seed derives names the given seed of
its letter: ``the bundle entry `0:A/24/0:86:0` is on the given card, but no given seed derives
it: seed 2 (letter A) is given, but its child 24/0 is not this entry's (a wrong seed, or one
with a passphrase, which `export` takes none for): give the child's own words with `--seeds`
and `--child N=A/24/0` ``. A `--child` seed that is not the child it
declares (its letter differs, or it is not the hot child of the given
card) is refused with ``(a child derived without the parent's
passphrase, or with a wrong one, is another seed: re-derive child 24/0
from seed A with its passphrase, if it has one, at
m/83696968'/39'/0'/24'/0')``. A seat a plate alone fills on a card
that ties nothing to it is printed ``seat @1: filled by plate 2, sc:…
(nothing on this card ties this key to this wallet: …)``, with no
warning and no refusal; `--seat-check` (see `mr verify`) ties it, each
value naming its card's set id on a run of several cards, and a
differing value is refused. More than one positional card is refused ``… give one card per run
(`export` takes the others with `--card`)``; a chunk given twice, ``chunk 1 is given twice:
give each of the card's chunks once (chunks are numbered from 0)``.

A card with an epoch axis needs one of the tip (`--height`, `--time`),
`--epochs a..b` or `--exhaustive` (`--epochs` or `--exhaustive` beside `--time`
is a usage error, as beside `--height`); an epoch-less card defaults to
`--epochs 0..0` and refuses any other range. `--exhaustive` can write hundreds
of megabytes: when its stdout passes 1 MB, a stderr warning first says how
large ("`--exhaustive` writes about 956 MB to stdout (302 call lines): save it
with `> FILE` rather than printing it, then `grep '^printf ' FILE > calls.sh`
copies the calls"; when stdout is already a file or a pipe it says "which is not a
terminal here: keep that output as a file" instead). Beside every probe call
`export` prints the ready `mr export SAME_ARGUMENTS --next <k + 1>`
command (SAME_ARGUMENTS, in a command `export` prints, is this run's arguments less its `--next`, `--heir-file` and `--history` values): run it while a probe call finds any unspent output. Each card
prints the rule's `@i=` binding list after its set id and a seating
count with its scan time; seatings the card cannot decide (seats at one
origin path with nothing to tell their plates apart) are exported only
with `--try-seatings`, each labelled with its binding list and a ready
`member --for-spend` stem (`mr member MR1_CARD --network testnet
--for-spend --epoch EPOCH --slot SLOT --seeds "GIVEN_SEED_1" --keys
@1=PLATE_2`: the run's `--network`, a seed by its position in `--seeds`,
a key by its label), and a count above K! is refused with its scan
time. `--next` may be repeated with one k, each value naming a target
(`--next 1:0/0 --next 1:held:84:0`): the run emits the union of the
targets' descriptors; two different k are refused. `--history` leaves
the child discovery accounts out; a discovery account prints its own
`--history --next 0:ENTRY` command, and `--history`'s ready
next-window command keeps the run's targets. The Core rescan's imports
are printed the same way, `printf '%s\n' '<json>' | bitcoin-cli
-testnet -rpcwallet=WALLET_NAME -stdin importdescriptors` (up to 1,000
descriptors each), and the rescan rule's calls as `bitcoin-cli -testnet
-rpcwallet=WALLET_NAME rescanblockchain` and `bitcoin-cli -testnet
-rpcwallet=WALLET_NAME getwalletinfo` (Core refuses a call without
`-rpcwallet` while more than one wallet is loaded), after the line ``in each `bitcoin-cli` call, replace
WALLET_NAME with the name of the watch-only wallet created for this
scan (`createwallet wallet_name=WALLET_NAME`, above)``. `WALLET_NAME` is
a plain word in every shell, so a line pasted unedited only fails in
Core (no such wallet); `<name>` there was a redirection from a file.
A seventeenth seed is
refused: run `export` once per group of at most 16 seeds.
`--heir-file` warns on stderr that the file holds every address of the
set, and the card's strings and the plates in its spend lines, from which
every epoch can be rebuilt, not only those listed; when the run skips a
slot's members for the row check (below), it reads "privacy: this file
holds every descriptor but the skipped members' (named in the file), and
so every address of those descriptors, of these sets, …". A new file is created readable by its owner only (mode 0600 on
unix); a regular file of your own already at that path is made 0600 and
replaced, and the run says so ("heir file written (the `--heir-file`
path, replacing the file that was there)"). A FIFO of your own or a
device there is written to as it is, its mode untouched; a symbolic link is followed and
the same rule applies to its target. On Linux an anonymous pipe given
through a descriptor (`/dev/stdout`, `/dev/stderr`, `/dev/fd/N`,
`/proc/self/fd/N`, as in `--heir-file /dev/stdout | …`) is written to
whoever owns it, since no one can plant one at a path; a named FIFO
reached that way (`/dev/fd/N` on a FIFO with a name) follows the FIFO
rule below. Off Linux such a pipe of another user is refused as another
user's FIFO. The path is checked before
anything is printed: a folder, a link to nothing, a socket, a path in
no existing folder or in a folder you cannot write, a file, FIFO or
device you cannot write, and a regular file or FIFO of another user
(root included: `mr` does not take another user's file over, and a FIFO
another user planted at the path would receive every descriptor of the
set; both refused as "the `--heir-file` path is a file of another user:
…") are each refused, naming `--heir-file`. An `--epochs a..b` whose start is past
the last valid epoch of any given card is refused before any line; an end past it is warned of
and the range line says "(--epochs, clamped to the card's last valid
epoch L)". The file covers the whole run, so it is refused with a `--next`
target; with `--history` it holds window 0's main and probe calls and
then both history outputs.

A run that **scans none of a card's members** (a lost plate, a seed
given without its seat's plate, plates made for another network, only
undecided seats) is refused, exit 1, even when it still has bundle or
child discovery accounts (`--seeds` alone always brings discovery
accounts): those accounts are never used for seating and do not stand in
for the card's members. Before the refusal each card names every missing
seat and what fills it, "card 1: seat @1 (letter B, fingerprint …,
origin m/…) is missing: give its mk1 plate with `--keys`, or seed
B with `--seeds`" (`export` takes mk1 plates as keys, no record; the hot
seat also by its parent or `--child`, or, when a seed of the parent's
letter was given, "seed A was given, but its child is not this seat's …:
give the child's own words with `--seeds` and `--child N=A/24/0`"; the
same lines are warnings on stderr when stdout is redirected, so a terminal shows each once), and
says when plates were set aside ("… (check `--network`), or of an earlier or later set of this card's seats, fills no
seat"); a seat's line also carries the earlier-set note for a plate of another round of that seat, and, for a plate at the seat's path under the other coin type, the other-network sentence, so a saved stdout or heir file holds both, and on a run of several cards each set-aside warning is prefixed "card N [digest]: ". The refusal reads "nothing to export for card 1: no member of it
derives from the keys and seeds given …"; to scan only a bundle or
discovery account, name it with `--next 0:ENTRY` (an entry as the
checklist prints it, such as `A/24/0:86:0`, or a discovery account's
`LETTER/LEN/I:P:0`). A run left with no descriptor is refused
the same way: when every member the run names is invalid ("card 1: no
member is valid in epochs … ", or "… the `--next` targets name"), and
under `--history`, which leaves the discovery accounts out, when they
were all it had. With several cards (`--card`), one card's missing seat
refuses the whole run, its fully seated cards included: give the missing
seats, or leave that card out of the run. A refused run prints no scan
call, no discovery count line, and writes no `--heir-file`; since
`--heir-file` is refused with a `--next` target, a heir file of the
accounts alone cannot be written while a seat is missing (scan an
account with `--next 0:ENTRY` without `--heir-file`). A card with no
valid member beside cards that scan is named on stdout and as a warning
("card 1: no member the `--next` targets name is valid"). A card whose
`--next` member targets emit no member, none for want of a seat, and some
of them skipped (by the row check, below, by a written form that fails,
or by a row with no spending path) is named by each target's cause
instead, "card 1: no member the `--next` targets name is emitted: (0, 1)
the row check refuses it (owner policy; no descriptor can be written for
it); (21, 2) invalid" (the other causes: "its written form fails (an
internal error; keep this card)", "its row leaves no spending path"), and
is not refused for want of a seat: a seat missing from every seating of
such a target still gets its "card 1: seat @1 (…) is missing: …" line, for
its remedy; in a run left with no descriptor the refusal says "(each
card's cause is named above)", or, with a seat of some card missing,
"(each card's missing seats or cause are named above)". A card whose
range holds valid members, every one of them skipped (by the row check,
a written form that fails, or a row with no spending path), is never
called invalid: it is named "card 1: no member in epochs 13 … 14 is
scanned: each valid one is skipped (`mr decode` on the card names each
slot's cause); keep this card: its skipped members may hold funds" (the
line ends at "cause)" when every skipped member is a no-path row's), on
stdout, as a warning and in the heir file, and is not refused beside
cards that scan. A run left empty by such cards (or by them and cards
with no valid member) is refused, exit 1, "nothing to export: no member
of the given cards is scanned (each card's cause is named above)", the
keys and seeds not being at fault; with a seat of some card missing (the
card's own missing-seat lines print, never the want-of-seat refusal for
it), "nothing to export: no descriptor of the given cards, their
seatings or bundle entries derives from the keys and seeds given (each
card's missing seats or cause are named above)".

**Members the row check refuses** (a card of another release: `create`
refuses such a row). `export` prints §4's warning on stderr, as `decode`
and `verify` do, "slot 1, epoch 0: \<cause\>: owner policy, which `create`
refuses; recovery skips this row's members that fail it and derives the
rest" (in a run of several cards each such warning, the card's own hash-fragment
(``this card's template has a hash fragment: …``) and shared-origin-path
(``@0 and @1 share the origin path …``) warnings and the coin-type warning
(``warning: card 1 [5bdd396d]: this card's origin paths carry coin type 0' (mainnet), but
--network is signet: …``) among them, and each
written-form note after its "note: ", starts "card 1 [5bdd396d]: ", so
the same text for two cards prints once per card; a duplicate row's ends "…; recovery derives its members as any
other's", and those members are scanned; a row with no spending path keeps
"…; recovery derives every other member and names this one"). A script
over the size limit is named "its P2WSH script is over 3,600 bytes, which
is not standard", or, for a bare `sh()` body, "its P2SH script is over 520
bytes, the most a spend may push" (a plain `sh(multi(…))` of 16 keys or more), never
"not well-typed". A bare `sh()` slot whose body is not a plain `pk`, `pkh`, `multi` or
`sortedmulti` (a lock makes it miniscript, which Bitcoin Core does not scan there) is the
slot's own refusal, slot 0 counting as a row: "slot 1: its bare `sh()` body is not a plain
`pk`, `pkh`, `multi` or `sortedmulti`, so Bitcoin Core cannot scan it: owner policy, which
`create` refuses; recovery skips every member of this slot and derives the rest", every
member of the slot skipped from epoch 0, past the slot's last valid epoch too (never named
invalid there), in the "skipped:" line with that cause; `member` and `address` refuse such
a member, ``slot 1: its bare `sh()` body is not a plain `pk`, `pkh`, `multi` or
`sortedmulti`, so Bitcoin Core cannot scan it``. The row check runs at epoch 0 and at the slot's last
valid epoch; a cause other than the size fails every member of the slot,
and the size alone grows with the epoch, so the slot is skipped from
epoch 0 or from the first epoch over the limit. Each member the row check
refuses at its own epoch is put into no call or output: no main or probe
scan, no Core import, no address-index list, no heir-file descriptor.
`export` names them once per card and slot, on stdout and as a warning on
stderr, whatever the number of seatings: "skipped: slot 1 of card
5bdd396d at epochs 0 … 12 (owner policy, which `create` refuses: \<cause\>):
no call here takes them; keep this card: its skipped members may hold
funds; for a member's descriptor, run `mr export SAME_ARGUMENTS --next
0:5bdd396d:EPOCH/1`, EPOCH one of those epochs". The line ends at "may
hold funds" in the heir file, and in a run whose `--next` targets are the
slot's skipped members. Such a member's descriptors are printed only for
a `--next` member target, on stdout with the descriptor list (before the
refusal in a refused run), per seating: "member (1, 1) [card 5bdd396d]
is skipped (owner policy, which `create` refuses: \<cause\>); its
descriptors, for a recovery by hand with other tools:", then "  receive:
\<descriptor\>" and "  change: \<descriptor\>" (`h` steps, checksummed), the
tag "[card \<d8\>, seating \<k\>]" with several seatings. Where md-codec
writes no script for it, one head per target ends "…; no descriptor can
be written for it (\<reason\>)", \<reason\> "it is not well-typed", "its P2WSH
script is over 3,600 bytes, which is not standard", "its P2SH script is
over 520 bytes, the most a spend may push" or "a sortedmulti out
of place, which md-codec does not write"; a seating with seats missing
gets "…; no descriptor can be written for it: seat @1 missing" ("seats
@0, @2 missing" for several) while the target prints under another
seating, and a target no seating fills gets one head, "…; no descriptor
can be written for it: no seating fills it (seat @1 missing)" (undecided
seats are named so: "(seats @0, @1 undecided)", "(seat @1 undecided)", and
"(seat @0 missing; seats @1, @2 undecided)" for both kinds). A target
whose receive and change lines print is emitted; a run whose only
members are such targets prints their lines, no call, closes with
"nothing to scan: the members the `--next` targets name are skipped
(above)" and exits 0. A skipped target never stands in for a member the
card lacks a seat for: beside a target with a seat missing the run is
refused as above. On a card any of whose rows the row check refuses, the
"finds nothing" footer adds "a row the row check refuses (§4's 'owner
policy' warning above; a 'skipped: …' line where the run reaches its
slot), or a slot whose written form fails (its 'note: … internal error'
line above), is not scanned: do not take this run as empty, and keep
this card", whatever the run's `--epochs`; a card with a slot whose
written form fails adds it too. `member` (with or without
`--for-spend`) and `address` refuse such a member, exit 1. A call whose
JSON would pass Bitcoin Core's 32 MiB request cap is split (only a probe
call of very long descriptors can), and one whose single descriptor
would pass it is refused (no card reaches it).

Each bundle entry's account gets a restore line per purpose printed (a
child entry is derived at all four purposes, so it gets four lines, its
written purpose first), naming the purpose and the account. A seed's own
entry: "restore this wallet in any BIP 84 wallet, account 0, from seed A's
words with its passphrase if it has one; it needs no card, no
registration and no migration". A child entry (the cheap hot wallet)
names the child, never the parent's own account: "restore this wallet in
any BIP 86 wallet, account 0, from its BIP-85 child's words (the words of
child 24/0 of seed A; they have no passphrase of their own), or derive
that child from seed A's words, with its passphrase if it has one, at
m/83696968'/39'/0'/24'/0'; it needs no card, no registration and no
migration".

A cheap-wallet (child) entry's wallet is printed only from a parent
whose BIP-85 child has the entry's child letter and, where the card
declares the hot seat's fingerprint, that fingerprint. The hot child's own words, given without `--child` and seated at the
hot seat by the card's fingerprint, are the entry's source ("seed 1 (the
hot seat's own words, fp …; it filled hot seat @3 by the card's
fingerprint)"). A parent given
without its passphrase (`export` takes none) derives another child: its
wallet is not printed, and `export` says so on stdout ("…
it is not this entry's child, so its wallet is not printed; seed \<n\> is
not this card's parent, or its passphrase is wrong …: give the child's
own words with `--seeds` and `--child N=C/24/0`"). Stderr says it once
for the seed, in the seating's warning that names the letters ("seed 1
has letter C but its child 24/0 has letter H, not F: seed 1 is not this
card's parent, or its passphrase is wrong …"), not three times. The fingerprint is
checked only on the hot seat's own entry; a cheap-wallet-only entry, and
any entry on a `--no-fingerprints` card, is checked by its letter alone,
so a wrong parent whose child shares the letter (1 in 16) still prints.
