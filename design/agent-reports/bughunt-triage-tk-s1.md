## 3. Open product questions

- #41: should `@N=` explicit placement check `--search-address` against the asserted placement, or refuse the combination? The test accepts either (fix-41 refuses).
- #38: should a taproot `multi_a` card with a non-standard baseline use-site be restored faithfully (fix-38) or refused? The test accepts either, plus a `/<0;1>/*` control that must still restore.
- #42: when the own slot's 65 bytes match but the engraved fingerprint differs, refuse with exit 4 (fix-42) or keep the output and only drop the "(verified)" label with a warning? The test accepts either.
- #47: should `verify-bundle --expect-wallet-id` share restore's `decode_wallet_id_prefix` (reject empty and more than 16 bytes) so both commands agree?
- #14: in the multisig `Err` arm, is the placeholder `md1_origin_match` row `passed: true` "skipped" (like its siblings, as in fix-14) or should it fail?

## 4. Noticed, not tested

- The taproot Template arm (#38 / #53 site) also ignores key ORDER: `tr(NUMS,multi_a(2,@1,@0))` would be rebuilt as K0,K1, a different script because `multi_a` is order-sensitive; `plain_template_from_tree` guards identity indices for wsh but nothing does for tr.
- `emit_candidate_list` (restore's enumerate listing) also writes straight to stdout and ignores `--output`, as #10 does; my fixtures did not reach a listing.
- Single-sig template `restore` prints "UNVERIFIED: no --expect-wallet-id supplied" even when `--expect-fingerprint` was given, so the banner misdescribes the ignored flag (part of #2).
- `verify_singlesig_template` uses plain `hex::decode` for `--expect-wallet-id`, so it also lacks restore's more-than-16-bytes refusal (same family as #47).
